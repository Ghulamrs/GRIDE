1. What the toolchain is

The toolchain is three command-line compilers plus a set of tools. The IDE runs the right compiler for a file, shows what it said, and runs the program when the target can run on this machine.

ProgramWhat it is
c90The C compiler. ISO C 90. Four targets.
cpp11The C++ compiler. ISO C++ 11. Four targets.
shalimarThe Shalimar compiler. Three host targets plus tms6747.
masm, linkThe x86-64 assembler and linker.
asm6x, lnk6xThe C6000 assembler and linker.
vm6747, sim6747The C6747 emulator (runs assembly text) and simulator (runs a .out).
c2sThe C89 ↔ Shalimar converter.
RTS6x, Shalimar runtimesThe C6747 runtime library and the Shalimar runtime archives.

In White (RIDE): the editor is RIDE.exe (windowed on Windows; the console editor on Unix), and RIDEConsole.exe is the console editor on Windows. Black and Grey: see their own guide (Help > View Help).

Everything the IDE does, you can do from a shell (chapter 18). Each tool runs alone and reports on its standard streams.

2. What a compiler takes as input

A compiler's input is source text, options and the headers its includes reach. Nothing else: the command line is all it sees.

Source text. The suffix sets the language. Each compiler refuses a language that is not its own:

  • c90 takes .c (and .h). It refuses .cpp, .cc, .cxx, .hpp, .hh, .hxx by name and points you at cpp11.
  • cpp11 takes .cpp and its family. It refuses .c by name, because C read as C++ can be quietly miscompiled where the languages disagree. The message points at c90.
  • shalimar takes .shl and .shm (the suffix the phone app writes). Nothing else.

Objects and libraries are inputs to the link step only. cpp11 sorts .o, .obj, .a and .lib out of its inputs and passes them to the linker.

Options. What to produce (-S, -c, or neither), where (-o), for which target (-arch; --target for shalimar), macros (-D, -U), header directories (-I), and how much to say (-nologo, -time). Part IV has the full list.

Headers. System headers are found beside the compiler (chapter 10). Your own headers are found through -I directories and the directory of the including file.

A compiler does not take a directory to build, search libraries by convention (you name them), or read CFLAGS or other ambient variables, except the include-path overrides (chapter 10).

3. What a compiler produces

A compiler produces one of three things, chosen by a flag:

FlagOutput
-SAssembly. One .s per input (.asm for the MASM spelling on x86_64-windows).
-cObjects. The assembly goes through the native assembler: one .o (Unix) or .obj (Windows) per input. No link.
neitherA program. All inputs are compiled, assembled and linked into one program, named by -o (default a.out; a.exe on Windows).

The compiler's own product is the assembly; objects and programs also need the native tools. So the Assembly tab works for every target, but "run" only where this machine has the tools.

Debug information (-g, or a Debug build) goes into the assembly and objects where the target can carry it (Part V).

4. The pipeline inside a compiler

All three compilers run one pass per stage, with no separate intermediate representation:

Driver → Preprocessor → Lexer → Parser (+ type work) → Backend
  • Driver: reads the command line, picks language, target and output kind, and runs the stages and the native tools.
  • Preprocessor (then the lexer): expands macros and handles #include, #if, #define and the rest. It leaves #line records for the original file, line and column. Shalimar has no preprocessor.
  • Parser: builds the syntax tree and does all type work. So a diagnostic and the generated code always agree on what a construct meant.
  • Backend: writes assembly for the chosen target.

Diagnostics and the debug line table use the same source map, so they always agree. Control flow is shared by all targets; expressions and calls are per target, where ABIs differ. So x86_64-linux and x86_64-windows share one instruction stream and differ only in spelling (GNU or MASM).

The compiler writes assembly. It does not assemble or link; it calls other tools for that.

Linking

  • Windows Release: link (LINK; its output matches Microsoft's on its own test set).
  • Windows Debug: Microsoft's link.exe /DEBUG. It writes the .pdb that cdb reads; LINK does not.
  • Linux: the host driver (cc/gcc), or clang++/g++ for C++.
  • macOS: clang++.
  • A link of C++ objects always goes through the C++ driver, so the C++ runtime is pulled in.

In White (RIDE): settings.json names the two tools, "assembler": "bin/masm.exe" and "linker": "bin/link.exe". Tools > Assembler for x86_64-windows... changes or clears the assembler. If masm or link itself fails and the compiler found no fault in the source, the editor asks: "The project's own masm and link did not build it. Use Visual Studio's ml64 and link.exe for this build instead?" Yes builds again with Microsoft's tools. "askNative": false in settings.json never asks and lets the build fail. It never asks for the program's own link errors (a missing main, an unresolved or duplicate symbol, a library for another platform), which Microsoft's tools refuse too, and never for a cl build. Black and Grey: see their own guide (Help > View Help).

Finding Visual Studio

The compiler finds Visual Studio itself through vswhere (pinned to VS 2022, never PATH) and runs the step in a shell that sourced vcvars64.bat, so any build works like one from a developer prompt.

The C6000 target

For tms6747 the tools are the toolchain's own on every host: asm6x assembles each .s, lnk6x links the objects against RTS6x into a .out, sim6747 runs that .out, and vm6747 runs the assembly text directly. TI's own tools can also assemble and link the .s into a chip binary (chapter 25).

What runs at once

  • A project build runs one compiler command per group, in order.
  • cpp11 compiles and assembles its files on a thread pool: one thread per file up to the core count, one thread below four files. -j n asks for another count.
  • c90 and shalimar go file by file.
  • In White (RIDE): a tms6747 group runs each source as its own -S command, in parallel up to the core count, writing output in source order. Then one asm6x and one lnk6x command take them all.

"Runs here" is a fact about this machine's tools, not the compiler. On Windows, arm64-darwin stops at -S.

Part II — The three languages: what each supports, and what it does not

Each compiler refuses by name and never accepts quietly: an unsupported construct stops the build with a message.

7. C — c90

Standard: ISO C 90 (ANSI C / C89), all of it.

Supported:

  • Types: integer and floating types, struct, union, enum, bit-fields, pointers, arrays, function pointers, const/volatile.
  • The full expression grammar, with C's integer promotions and usual arithmetic conversions.
  • All statements, including switch with fall-through and goto with labels.
  • Storage classes: auto, register, static, extern, typedef.
  • A complete preprocessor: object- and function-like #define, #include, #if/#ifdef/#elif/#else/#endif, #line, #error, #pragma, # (stringise) and ## (paste).
  • Variadic functions, both calling and defining (va_start/va_arg/va_end).
  • A character constant is an int, as C90 says.
  • The standard headers in lib/: stdio.h, stdlib.h, string.h, math.h, ctype.h, assert.h, errno.h, limits.h, float.h, stddef.h, stdarg.h, time.h, setjmp.h, signal.h, locale.h, and the rest.

Not supported (C99 and later):

  • // comments are not guaranteed as a dialect feature (only what the lexer happens to accept).
  • long long is not a standard type name to rely on.
  • No mixed declarations and code, no variable-length arrays, no C99 inline.
  • No _Bool or <stdbool.h>, no restrict, no _Complex.
  • No designated initialisers, no compound literals.
  • No <stdint.h> guarantees beyond what lib/ provides.
  • No C++: a .cpp is refused by name, pointing at cpp11.
  • Not an assembler or linker: it emits assembly and calls the native tools (chapter 5).

Targets: all four: x86_64-linux, x86_64-windows, arm64-darwin, tms6747.

Debug information: DWARF on the two GNU targets; CodeView on x86_64-windows in the GNU spelling a Debug build uses (none in the MASM spelling); none on tms6747 (the emulator and simulator run it, no debugger reads it).

8. C++ — cpp11

Standard: ISO C++ 11, minus the exclusions below, with a simplified library in include/. Part X goes feature by feature.

Supported — most of C++11:

  • Classes: data and function members, access control, constructors (default, parameterised, copy, and move where the shapes are simple), destructors, this, member initialiser lists, nested classes, friend.
  • Inheritance: single and multiple. Virtual functions with vtable dispatch; pure-virtual functions and abstract classes.
  • Virtual (shared) base classes: full Itanium virtual inheritance on the three Itanium targets (secondary vtables, the VTT, _ZTv virtual thunks, construction vtables, C2/D2 constructors taking a VTT), matching clang's tables.
  • Templates: class and function templates, explicit specialisation (template <> struct Box<int> {…}), partial specialisation, non-type parameters, instantiation, and two-phase name lookup as far as C++11 requires.
  • Exceptions (on the three Itanium targets, with each target's own tables): throw/try/catch; unwinding runs destructors; catch by value (copied from __cxa_begin_catch) and by reference; a thrown pointer; rethrow; noexcept/throw() call std::terminate on an escaping exception; a destructor that throws during unwinding terminates.
  • RTTI: typeid (static and dynamic), type_info, dynamic_cast to a pointer along a single-base chain, including dynamic_cast<void*> (most-derived).
  • operator new/operator delete: replaceable global forms, class-specific forms, and placement new, each dispatching to the right operator.
  • Other C++11: lambdas, auto variables, nullptr, enum class and underlying types, alignas/alignof, static_assert, range-based forms as far as the library supports them, references and rvalue references where the shapes are simple, member and function pointers (including pointer-to-virtual-member dispatch), and constexpr in the forms the compiler implements.
  • Library in include/:
    • <cstddef>, <cstdlib>, <cstring>, <cmath>, <cctype>: each the C header wrapped into std.
    • <string> as a class; <utility>, <algorithm>.
    • <vector> (a growing array), <map> (a sorted vector of pairs), <set> (a sorted vector). Every iterator is a pointer.
    • Streams: <iostream>, <ostream>, <istream>, <sstream>, <fstream>, <ios>, <cstdio>, with std::cout/cin/cerr as file-scope objects.

Refused — the exclusions (each by name):

  • dynamic_cast to a reference. It has no null to return. Use the pointer form and test for null.
  • dynamic_cast naming a class with more than one base. It needs __vmi_class_type_info, which is not emitted.
  • A member class template. A member function template is fine.
  • A trailing return type, auto f(int) -> int.
  • Objects that would run code before main, in the forms the compiler does no dynamic initialisation for.
  • C++14 and C++17 forms (for example C++14 constexpr relaxations). The message names the standard version.
  • Eight keywords the parser has no rule for yet. Refused as "does not begin an expression" or "not supported yet".
  • volatile is parsed but dropped: it does not change code generation. Do not rely on it for memory-mapped I/O.
  • Target-only refusals. For example, a polymorphic virtual base is refused on x86_64-windows (Microsoft ABI); the Itanium targets accept it.

If cpp11 refuses something, it says so by name. When unsure about a construct, compile a one-line program; some refusals sound broader than they are.

9. Shalimar — shalimar

Shalimar is a small numeric language. The full language is Appendix A - The Shalimar Language, its own complete reference. This chapter gives its shape and limits.

The language. A program is a set of functions; it starts at main.

  • A function: fun <capture> = name(params) { … }
  • Assignment: name : value
  • ? prints.
  • while and if; arithmetic and comparison operators; numbers, strings and arrays.

n : n + 1 is an assignment in Shalimar but a goto label in C, so the editor indents Shalimar by its own rules.

The runtime. A Shalimar program links against a runtime archive (shmrt-<target>). It owns main, formatting, console I/O, arrays and failure paths.

uses (borrowing). A file borrows library functions by name. A borrowed name resolves against the runtime and cannot also be a variable. The compiler checks that each call names something the file borrowed, and reports it at that point.

Limits, by design:

  • No block comment, no character literal, no escapes in strings, no preprocessor.
  • Two Shalimar files cannot link into one program. Every unit exports the same three startup symbols, the runtime owns main, and there are no cross-file declarations to check a call against. Shalimar beside C means two programs.
  • No debugger. Shalimar carries no debug information on any target; the Debug menu refuses it by name.
  • No C-style pointers, manual memory, struct/union types or hardware access.
  • The compiler follows the interpreter. Any difference is a conformance bug, not a dialect.

Targets: the three host targets and tms6747. On tms6747 a program runs on vm6747, which assembles it with the C6000 runtime (shmrt-tms6747). Its .out links the same runtime as shmrt6x.lib (shmrt6xd.lib in Debug) ahead of RTS6x, and runs on sim6747. A Debug build stops itself on the C6000 too.

10. Header routing: lib/ is C, include/ is C++

The folder decides a header's language. The compiler decides which folders it searches.

FolderHolds
lib/The C standard headers (stdio.h, string.h, assert.h, …). The name is historical.
include/The C++ standard headers (<vector>, <new>, <typeinfo>, <cstdio>, …).
  • c90 searches only lib/. #include <stdio.h> → lib/stdio.h. It never looks in include/.
  • cpp11 searches include/, then lib/. <vector> → include/vector; <cstdio> → include/cstdio, which pulls in lib/stdio.h.
  • Both search your -I directories first, so a project header wins over a standard one.

How the folders are found at run time:

  1. The environment overrides CPP11_INCLUDE and CPP11_LIB.
  2. Beside the compiler, then one directory up (../include, ../lib). A pair is accepted only if include/ has vector and lib/ has stddef.h.
  3. The paths built into the compiler.

So bin\cpp11.exe finds ..\include and ..\lib, never the Shalimar runtime folder bin\lib\ (no stddef.h).

Part III — Projects: the .pro file, and making and updating one

Chapters 11-13 are about White's editor. Black and Grey: their .pro formats differ; see their own guide (Help > View Help).

11. The project file (.pro)

In White (RIDE): two files steer a build, the installation's settings.json and the project's <name>.pro.

settings.json

It sits one directory above bin\, beside include\ and lib\, and is read for every compile. In White (RIDE), the editor writes the defaults on first run.

{
  "include": "include",
  "lib": "lib",
  "vcvars": "",
  "compiler": "auto",
  "indent": 4,
  "tabs": false,
  "font": "",
  "includes": ["C:/work/common/include"],
  "libraries": ["C:/work/common/lib/mathlib.lib"]
}
  • include / lib: cpp11's headers (C++ and the C ones they wrap) / c90's headers. Relative to the file unless absolute. Passed as -I; the compilers also find them unaided. Set by Tools ▸ Header directories....
  • vcvars: empty until Visual Studio cannot be found; then the vcvars64.bat to use. Set by Tools ▸ Locate vcvars64.bat....
  • compiler: the start-up choice: auto, c90, cpp11, shalimar, msvc or c++. The Tools menu writes it when no project is open; an open project's own choice wins.
  • indent, tabs: file layout unless the project says otherwise. font: set by Tools ▸ Font....
  • includes / libraries: header directories and libraries for every compile and host link, searched and linked after a project's own. Set by Tools ▸ Shared include paths... / Shared libraries....

The .pro

One JSON object in <name>.pro, in the project's directory:

{
  "name": "demo",
  "toolchain": "auto",
  "arch": "x86_64-windows",
  "indent": 4,
  "tabs": false,
  "groups": {
    "Sources": ["greet.c", "main.c"],
    "Headers": ["greet.h"]
  },
  "include": ["include", "../common"],
  "libraries": ["lib/mathlib.lib"],
  "build": { "target": "demo", "groups": ["Sources"] }
}
  • name: shown in the title bar.
  • toolchain: auto (suffix decides; almost always right), c90, cpp11, shalimar or msvc (cl). A named one forces every auto group. Set by the Tools menu or Ctrl+K.
  • arch: x86_64-windows, x86_64-linux, arm64-darwin or tms6747. Set by the Target menu or Ctrl+T. Absent, or another machine's host target: this machine's host target is used. tms6747 is always kept.
  • indent, tabs: absent means settings.json decides.
  • groups: named file lists, shown as headings in the left pane, and the unit the build selects. A group can override the compiler: "Legacy": { "files": [...], "toolchain": "msvc" }.
  • include: the project's header directories, relative to it, searched first in order: -I to c90, cpp11 and the host's C++, /I to cl; none to shalimar. Set by Tools ▸ Project include paths....
  • libraries: linked after the objects (.lib on Windows, .a on Unix). A project with any is built as objects and linked by the host's linker. Ignored for tms6747. Set by Tools ▸ Project libraries....
  • open: the file that opens with the project; saved on close or exit (Ctrl+Q). Absent: the file defining main (int main(, or fun <> = main() in Shalimar), else the first file.
  • build: target names the program; groups lists the groups compiled into it. Others, and headers, are skipped. A new project builds Sources into a program of its own name.

Build project (F4) and Run project build the named program; Run file (F5) on a project source runs the project. Mixed C/C++: chapter 13.

It deliberately lacks: compiler flags (no cflags, cxxflags, defines; use the command line, Part IV); build rules or steps (it is not make); more than one program; library targets and install rules; conditional files. Debug/release is an editor toggle, not a field.

12. Making and updating a project

In White (RIDE): all on the Project menu. Every change writes the .pro at once.

  • New…: pick a folder, give a name; writes and opens <name>.pro with an empty Sources group.
  • New File (Ctrl+N): creates an empty file (subdir/name allowed), adds it to the group its suffix suggests, opens it.
  • Add File: adds the open, saved file to a group you name.
  • Remove File: takes the open file out of the project; it stays on disk.
  • Save / Save as…, Open… / Close: as named.

The demo project in projects/c-demo/ shows a typical result. The status line shows language, configuration, compiler (* when the file chose it) and target.

13. Groups, the build target, and mixed C/C++

In White (RIDE): how a group builds depends on its toolchain.

  • auto, one language: that language's compiler.
  • auto, C and C++: split. C to c90, C++ to cpp11, objects linked. The console shows Sources (c90) and Sources (cpp11).
  • Named (say msvc): that compiler takes the whole group. The only way to make cl compile C as C++.

Shalimar cannot join C or C++. No compiler takes both, and every Shalimar unit exports the same three startup symbols, its runtime owns main, and it has no cross-file declarations. Shalimar beside C is two projects.

Debug info does not mix: cl writes CodeView, c90/cpp11 DWARF or CodeView by target, shalimar none. A mixed build debugs only as well as its weakest part.

Link driver: the C++ driver if any part is C++, else the C driver. The console prints linking with <driver>.

Part IV — Choosing a compiler, the command line, and building by hand

14. How the compiler is selected

In White (RIDE), highest authority first:

  1. Tools menu (project or global): a named compiler wins for every auto group. Default auto, shown with *.
  2. A group's own toolchain.
  3. The suffix: .c/.h → c90; .cpp/.hpp/… → cpp11; .shl/.shm → shalimar.
  4. The Language menu, for a misnamed file (a .h that is C++). It sets colouring, layout and, via Tools ▸ By language, the compiler.

Under auto, a .cpp never reaches c90 nor a .c cpp11; forced, the compiler refuses by name. Ctrl+K cycles compiler, Ctrl+T target, Ctrl+D debug/release. Black and Grey: see their own guide (Help > View Help).

16. cpp11 — command-line reference

      [-D n[=v]] [-U n] [-I dir] [-arch a] [-masm=m] [-g] [-nologo]

Each flag means what it means for c90. The differences:

  • Takes .cpp, .cc, .cxx; refuses .c by name.
  • .o, .obj, .a, .lib inputs go straight to the link.
  • System headers: include/ (C++), then lib/ (C).

Part VI — The C6000 target, the emulator, and real silicon

23. The TMS320C6747 / C6000 target

The C6747 is a C674x VLIW DSP in TI's C6000 family: up to eight units issue in parallel, instructions carry unit specifiers and || markers, branches have delay slots. c90, cpp11 and shalimar target it with -arch tms6747 (--target=tms6747 for shalimar).

The ABI matches TI's cl6x:

  • Arguments in A4/B4/A6/B6/A8/B8/A10/B10/A12/B12, then the stack from B15+4. 64-bit values in even:odd pairs.
  • A class of 8 bytes or less: returned in A5:A4, passed in a register or pair. Larger: via a hidden pointer in A4 (before this).
  • Scalars are near (B14-relative) data; TI section conventions.
  • wchar_t 16-bit unsigned, long 32-bit, long double 8 bytes, bool 1 byte, size_t = unsigned int.
  • TI's exception model (.c6xabi.extab/.c6xabi.exidx-style tables, TI's unwinder frame, __cxa_end_cleanup at cleanup pads).
  • Vtables, VTT, typeinfo and thunks laid out word for word as cl6x does, so objects mix with TI-built ones.

The assembly uses TI's spellings ($ for dots in names, .ref for undefined symbols, EXTU/CLR where an AND immediate does not fit). Every emitted .s assembles under cl6x.

24. The vm6747 emulator

vm6747.exe, a C674x instruction-set emulator, assembles the program in memory and runs it. No TI tools, any host.

vm6747 program.s                          (C or C++)
vm6747 program.s bin\lib\shmrt-tms6747     (Shalimar: runtime beside it)

It supplies the C6000 helpers (__c6xabi_div*, 64-bit shift/multiply), printf-class I/O, exit, a heap and argc/argv. It faults an unaligned load that silicon would allow. Its own choices: division by zero faults, abort returns 134, the heap is a fixed 16 MB, time() has its own epoch.

It is not not a debugger (debugging refuses tms6747 by name); not a chip image maker. It reads assembly text and runs over its own C library and exception runtime, so faults in asm6x, lnk6x or RTS6x run clean on it. sim6747 catches those: it runs the linked .out with TI's boot code and the real runtime (chapter 25).

In White (RIDE): Build > Emulate on vm6747 builds with -S and runs on vm6747. F5 / Run project builds with asm6x and lnk6x against RTS6x and runs the .out on sim6747. Build > Verify runs both and compares. The console shows the output and [program returned N]. Black and Grey: see their own guide (Help > View Help).

25. Real silicon: a .out from the editor, and the TI build path

Default build

A tms6747 project build makes a TI ELF .out with no TI tools:

  1. asm6x (matched to TI's object for object) assembles <program>.vm into a .obj beside each .s: $ asm6x N sources.
  2. lnk6x (matched to TI's byte for byte) links them with RTS6x: $ lnk6x N objects, rts6x.lib, then [linked <program>.out].

An assembler that refuses or a link that fails fails the build: what the emulator runs must be a TI program, or the emulator proves nothing.

The standalone script: ti-build

Makes a chip .out and Intel .hex from one file, using a TI Code Generation Tools (CGT) install already on the machine. It ships none of TI's tools. See bin\ti\TI-BUILD.txt.

bin\ti\ti-build.cmd  path\to\program.c        (or .cpp, or .shl)
  1. Finds the CGT: RIDE_TI_CGT (the CGT folder), cl6x on PATH, then C:\ti\ccs*\tools\compiler\ti-cgt-c6000_*. If none, it points to TI's free download.

Part VIII — The Shalimar ecosystem and the c2s converter

31. The map: what is inside the toolchain, and what is beside it

Inside GRIDE — the one toolchain all three outlooks drive: c90 (C90), cpp11 (C++11), shalimar (Shalimar, four targets), masm and link (x86-64 assembler, linker), asm6x and lnk6x (C6000 assembler, linker), vm6747 and sim6747 (C6747 emulator, simulator), c2s (C89 ↔ Shalimar), RTS6x (C6747 runtime), and the Shalimar runtimes shmrt-* in bin\lib\.

Beside it:

  • Compiler-S — the upstream compiler shalimar is built from (chapter 32).
  • The Shalimar iOS apps — a Swift interpreter running Shalimar on a phone. Shalimar is the original and the language authority (SHALIMAR_LANGUAGE.md); This manual's Appendix A is a checked copy. Shalimar-2 runs C on a phone: C → c2s → Shalimar → interpreter.

Compiler-S takes expected output from the app's interpreter; the document is the authority.

32. Compiler-S, shc and shalimar

Compiler-S compiles .shm/.shl to native assembly for arm64-darwin, x86_64-linux, x86_64-windows; shalimar adds tms6747.

Runtime. Programs link against shmrt-<target>, which owns main, number formatting, console I/O, arrays and failure paths. The compiler looks in lib/ beside itself, then ../lib. Without it, compiling works but linking fails.

Known divergence (docs/CONFORMANCE.md): t : s copies a string per the document and the compiler; the app's interpreter aliases it. The document and compiler are the reference.

Debugging. No debug information on any target, by decision; debugging refuses Shalimar by name.

33. The c2s converter — what it is

C89 source   →  c2s  →  Shalimar source     (CToS)
Shalimar     →  c2s  →  C89 source          (SToC)

A source-to-source translator; no machine code. It has its own C front end (lexer, parser, preprocessor, pre-scan) and uses Compiler-S's Shalimar front end. In White (RIDE), two Language-menu items run it on the open file.

  • C → Shalimar: carry what maps faithfully, refuse by name the rest, never change meaning.
  • Shalimar → C: adds a c2s_* runtime preamble (chapter 35).

34. c2s features — C → Shalimar, in detail

Control flow (Shalimar has no goto or labels):

  • switch where every case breaks → if/elseif/else.
  • break mid-arm → chain wrapped in while 1 { … break }. break and continue in one arm is refused; either alone converts.
  • Real fall-through → entry-index / done-flag shape, exact to C, mid-list default included.
  • Grouped labels (case 4: then default:) → one arm.
  • for, while, do-while, if/else carry; for i : a to b is kept where the counter does not escape.

printf becomes a generated function per format (e.g. print_1(a1: int)), shared when text and types match; argument order matches C.

carried:  %d  %i  %s  %c  %f  %.Nf  %%          (N up to 17)
refused:  %g  %e  %x  %ld  %u  %.3d
refused:  %4d   %-5d   %8.2f     (a WIDTH or a FLAG)

Shalimar's ? has no width, so %4d is refused; put spaces in the text. Precision works only on f (prec(N)). Spacing: ? adds a space after each item, so printf("value %d.\n", n) → ? "value" n "." prints value 5 .. Carried with a warning per printf, naming the line.

Overflow: int + - * go through c2s_add_int etc., which stop with the runtime's message and line instead of wrapping.

carried:  double/float (→ real), i++ as a statement,
          x = i ? 2 : 3 as a whole right-hand side
refused:  long, short, unsigned, static inside a function, goto,
          ++/-- inside an expression, ?: inside a larger expression

Position matters: x = 1 + (i ? 2 : 3) and a[i++] are refused.

Permissions (off by default; --pragmatic enables all) guard rewrites that change meaning slightly:

  • --allow-short-circuit — &&/|| → &/| (both sides evaluated); needed only where a side has an effect.
  • --allow-... narrowing — unsigned to Shalimar's number loses range.
  • char arithmetic — carried where safe.

Guards and macros: a guard holding only a definition (#ifndef M_PI / #define M_PI 3.14 / #endif) is dropped with a comment, or with a warning if the file has any #include. __LINE__/__FILE__ are expanded. Other conditionals stop the run.

Diagnostics: refusals are ConversionError C2100 with line and column. --lines prints an out: in line map.

35. c2s features — Shalimar → C

  • Emits C89 accepted by -std=c89 -Wall -Wextra -pedantic -Werror.
  • Includes only the preamble parts used (an integer-only program gets no floating-point globals, so no warnings).
  • elseif chains become flat else if; an else with a lone if collapses; an else with more statements keeps braces.
  • No faithful C form: refused with C2100.

Language note: Shalimar folds -x to 0 - x for non-literals, so -0.0 returns as +0.0.

36. Using c2s from the command line

c2s.exe is in bin\:

c2s program.c              C → Shalimar (writes the .shl/.shm form)
c2s program.shl            Shalimar → C (writes the .c form, with the preamble)
c2s --pragmatic program.c  allow the meaning-changing rewrites
c2s --lines program.c      also print the out:in line map on stderr
c2s --canon program.c      print the parsed C back as C (the lowered form)

It runs without c90 or shalimar.

Part X — C++11 in cpp11, feature by feature

cpp11 accepts C++11 minus a documented list (Part II chapter 8). The full source-derived list is the compiler's docs/EXCLUSIONS.md. If unsure, compile a probe: a refusal reads broader than it fires.

47. Types, declarations, expressions

  • Accepted: auto variables (auto x = 3;); decltype (ordinary forms); nullptr, std::nullptr_t; enum class and an enum base (enum class C : unsigned { A };); alignas/alignof on a class, member or object; static_assert; constexpr in the C++11 forms implemented.
  • Refused: C++14 constexpr relaxations (naming the version); a trailing return type auto f(int) -> int (write int f(int)).
  • volatile: parsed, then dropped (no effect on codegen). Not for memory-mapped I/O.

48. Classes, inheritance, special members

  • Accepted: members, access control, this, nested classes, friend; constructors (default, parameterised, copy; move where simple), initialiser lists, destructors; single and multiple inheritance, virtual and pure-virtual functions, abstract classes (vtable dispatch).
  • Virtual bases: accepted on the three Itanium targets with the real machinery (secondary vtables, VTT, _ZTv virtual thunks, construction vtables, C2/D2 constructors taking a VTT). On x86_64-windows a polymorphic virtual base is refused by name (.notarget).
  • = default / = delete: accepted in the implemented forms. One that would link but never be callable is refused at the declaration, by name.

49. Templates

  • Accepted: class and function templates; explicit specialisation (template <> struct Box<int> {…};); partial specialisation; non-type parameters; member function templates.
  • Refused: member class templates (move to namespace scope); template <> where a parameter list is expected (explicit specialisations still compile).

50. Exceptions

  • throw/try/catch: accepted; unwinding runs destructors.
  • Catch by value (copied from __cxa_begin_catch), by reference, thrown pointers, rethrow: accepted on the Itanium targets.
  • noexcept/throw(): accepted; an escaping exception calls std::terminate.
  • A destructor throwing during unwinding terminates (Itanium targets).
  • x86_64-windows refuses some exception shapes by name (.notarget).

51. RTTI

  • Accepted: typeid (static, dynamic), type_info; dynamic_cast to a pointer along a single-base chain, including dynamic_cast<void*> (null on failure).
  • Refused: dynamic_cast to a reference (use the pointer form, test for null); dynamic_cast naming a class with more than one base (needs __vmi_class_type_info, not emitted).

52. new / delete, lambdas, and the library

  • Global, class-specific and placement operator new/delete: accepted (chapter 40).
  • new[]/delete[] with an array cookie: accepted. Arrays of a class with a destructor (local, new[], static) run their destructors.
  • Lambdas: accepted.

The library in include/ is a working subset, not a conforming one:

  • <cstddef> <cstdlib> <cstring> <cmath> <cctype>: C headers wrapped into std.
  • <string>: a class.
  • <utility> <vector> <map> <set> <algorithm>: vector = growing array, map = sorted vector of pairs, set = sorted vector, iterators are pointers.
  • <iostream> <ostream> <istream> <sstream> <fstream> <ios> <cstdio>: std::cout/cin/cerr are file-scope objects.

53. The exclusions, gathered

Every refusal is by name, with a line:

  • trailing return types; member class templates;
  • dynamic_cast to a reference or naming a multi-base class;
  • pre-main dynamic-initialisation forms not implemented;
  • C++14/C++17 syntax (naming the version);
  • eight keywords with no parser rule yet ("not supported yet");
  • volatile semantics (dropped);
  • x86_64-windows only: polymorphic virtual bases, some exception shapes.

cpp11 never miscompiles an unsupported construct: it refuses it.

Part XI — The ABIs: how each target passes arguments and lays out types

The toolchain's compilers implement each target's real ABI (registers, results, type widths, name decoration), so their output links with the platform's own tools and libraries.

54. Why the ABI is per-target and the instructions are (mostly) shared

Backends share one statement walk; expressions and calls are per-target (Part I chapter 4). The two x86-64 targets share one instruction stream, spelled GNU or MASM, and differ only in argument registers and type widths. arm64-darwin and tms6747 each have their own instructions and ABI.

55. Type widths across the four targets

Same on all four: short 2, int 4, long long 8, bool 1, char 1 (signed on the three non-C6000 targets).

  • Args x0..x7, result x0 (x1:x0 pair); float v0..v7. Callee-saved x19..x28; frame x29/x30.
  • Apple's variations (stack argument passing, char signedness) are followed.
  • Assembled and linked by clang. A real link gathers DWARF into a .dSYM: dsymutil runs when the driver compiled the sources; an objects-only link requests the debug map before the objects are removed.
  • Native on Apple-silicon Macs.

58. tms6747 — the C6000 EABI

A VLIW DSP with register files A and B. The compiler implements TI's EABI, verified word for word against cl6x:

  • Args A4 B4 A6 B6 A8 B8 A10 B10 A12 B12, then the stack from B15 + 4; 64-bit values in an even:odd pair.
  • Structs: ≤ 8 bytes returned in A5:A4 and passed by value in a register or pair; larger returned through a hidden pointer in A4, the first parameter, before this.
  • Near data: scalars DP-relative through B14, in TI's near sections.
  • Callee-saved: A10/B10/A12/B12 and the frame registers when used across a call (shalimar too, so a TI-compiled caller of a Shalimar comparator is safe).
  • Exceptions: TI's tables (.c6xabi.extab-style scope descriptors, an index entry per function, __cxa_end_cleanup at a cleanup pad).
  • C++ layout (vtables, VTT, typeinfo, virtual thunks) matches cl6x; objects interoperate with TI-built ones.
  • Assembly in TI syntax: $ for dots in names, .ref for undefined symbols, EXTU/CLR where an AND immediate has no room, || and unit specifiers.

So the .s assembles under cl6x/asm6x and links under lnk6x with TI's runtime (Part VI). ABI-compatible, not byte-identical (Part VI chapter 25).

59. Name decoration (mangling)

  • C: undecorated (a leading underscore where the platform uses one).
  • C++: Itanium (_Z…) on the three Itanium targets; Microsoft (?…) on x86_64-windows, checked against cl's symbol tables.
  • Shalimar: every unit exports the same three startup symbols and the runtime owns main, so two Shalimar objects do not link together (Part II chapter 9).

A diagnostic gives file, line, column, severity and message. The caret marks the column:

Part XIII — The libraries that ship: lib/ (C) and include/ (C++)

65. lib/ — the C standard headers

The real C90 headers - printf/scanf and FILE I/O; malloc, free, qsort, bsearch, abs, atoi, strtol; str* and mem*; sin, cos, sqrt, pow, floor; va_*. c90's only system directory; cpp11 searches it after include/.

assert.h   ctype.h    errno.h    float.h    limits.h   locale.h
math.h     setjmp.h   signal.h   stdarg.h   stddef.h   stdint.h
stdio.h    stdlib.h   string.h   time.h     (and the platform's io/fcntl)

The platform's C runtime implements them; on tms6747 the emulator supplies it (Part VI). cpp11 takes a directory as C headers only if it holds stddef.h, so bin\lib\ is never mistaken for lib\.

66. include/ — the C++ headers

Searched first by cpp11.

  • C wrappers: <cstddef>, <cstdlib>, <cstring>, <cmath>, <cctype> pull their lib/ names into std.
  • Containers: <string>; <vector> (growing array); <map> (sorted vector of pairs); <set> (sorted vector); <utility>, <algorithm> (what the containers need). Iterators are pointers; a working subset, not full implementations.
  • Streams: <iostream>, <ostream>, <istream>, <sstream>, <fstream>, <ios>, <cstdio>. std::cout/cin/cerr are constant-initialised, so nothing runs before main. if (stream >> v) works.
  • <new> (placement new) and <typeinfo> (typeid; Part X).

67. What is not in the library

  • Full <algorithm>, iterator hierarchy, <functional>/<memory> smart pointers.
  • <thread>, <mutex>, <atomic>, <chrono>, <regex>, <random>, <filesystem>.
  • Locales beyond <locale.h>; <stdexcept> classes beyond those declared.

A missing header fails at the #include, by name.

68. The Shalimar runtime as a "library"

The runtime shmrt-<target> in bin\lib\ provides main, ? formatting, console I/O, array operations and trapping arithmetic. Programs borrow it with uses (no preprocessor). On tms6747 it is .s files the emulator assembles; on hosts, a .lib/.a. The -debug runtime adds a dormant debug session; compiler output is identical either way.

Part XIV — FAQ: "why does it…"

Why three compilers? Three languages; C and C++ give the same syntax different rules. The suffix picks the compiler, and each refuses the others by name (Parts II, IV).

Why Visual Studio on Windows? Release builds use masm and link only. Debug builds (clang assembler, link.exe /DEBUG), cl builds and the vendor fallback need it; the compiler sources vcvars64.bat itself (Part V chapter 22). In White (RIDE): Tools > Locate vcvars64.bat... names an unusual location.

Why can't I step a Release build? MASM has no line table and ml64 cannot relocate CodeView. Debug builds (GNU spelling) step in cdb, C and C++ (Part V chapter 22).

Why does long change size? 32-bit on Windows and C6000 (LLP64), 64-bit on Linux/macOS (Part XI chapter 55). Where the size matters, use the fixed-width types of <stdint.h>.

Why is volatile ignored in cpp11? Parsed and dropped; do not rely on it for memory-mapped I/O (Parts II, X).

Why does <thread> fail? Not shipped (Part XIII chapter 67).

Why won't two Shalimar files link? Each exports the same startup symbols, the runtime owns main, and there are no cross-file declarations (Parts II, III).

Why no .exe on tms6747? vm6747 runs the .s in memory. For .out/.hex use bin\ti\ti-build.cmd with a TI CGT (Part VI).

Same output as TI's compiler? No; ABI-compatible with cl6x, not byte-identical (Part VI chapter 25).

Why does converted printf add a space? ? spaces every item; c2s warns per printf (Part VIII chapter 34).

Where do files go? Compilers in bin\, Shalimar runtime in bin\lib\, include\ and lib\ beside bin\. -S/-c output lands beside the source unless -o (Part I chapter 6). In White (RIDE): a project's program lands beside its .pro.

Without an editor? Yes: command-line tools. Part IV is the reference, Part IX the examples.
