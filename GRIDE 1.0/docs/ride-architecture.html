4 · Assembler, linker and runtime for each target, as RIDE builds it

x86_64-linux

  • Assembler and linker: the system's, through cc/c++
  • Runtime: glibc, libstdc++
  • Output: ELF program

x86_64-windows

  • Debug (-masm=gnu): assembler clang's, the object carrying CodeView; linker Microsoft's link.exe /DEBUG, writing the .pdb; debugger cdb (M10, 5.1)
  • Release (-masm=masm when Tools names an assembler, which the installed settings.json does): assembler masm MASM/src; linker link LINK/src if named under Tools, else Microsoft's link.exe. With nothing named cpp11 writes the GNU spelling, clang assembles, link.exe links
  • Prompted retry: when RIDE's own masm or link fails and the compilers found no fault, the editor asks and a Yes builds again through Visual Studio's ml64 and link.exe; RIDE names ml64 nowhere else
  • Runtime: the Microsoft CRT
  • Output: PE .exe

arm64-darwin

  • Assembler and linker: Apple's clang toolchain
  • Runtime: libSystem, libc++
  • Output: Mach-O program

tms6747

  • Assembler: asm6x ASM6x/src; output TI ELF .obj
  • Linker: lnk6x LNK6x/src (the default); TI's lnk6x when TI's compiler directory is named under Tools, or on a prompted retry after lnk6x failed
  • Runtime: rts6x.lib / rts6xd.lib RTS6x/src - itself compiled by cpp11 and assembled by asm6x; TI's rts6740_elf[_eh].lib when TI's directory is named
  • Shalimar also links shmrt6x.lib / shmrt6xd.lib - cpp11's output too (workspace.mk)
  • Output: .out, which Run hands to sim6747, beside the .s files Emulate on vm6747 runs

Edges the page used to leave out

  • cpp11 → RTS6x, shmrt-tms6747. The C6747 runtime a program links against is compiled by cpp11 and assembled by asm6x (RTS6x/Makefile); so is Shalimar's C6000 runtime (workspace.mk). A fault in the compiler reaches the runtime it links.
  • cpp11 standalone → TI lnk6x + rts6740. Run from a command line, cpp11 -arch tms6747 without -S links through TI's lnk6x against rts6740_elf[_eh].lib under CPP11_TI/CPP11_TILIB (Driver.cpp, linkTi). RIDE's build is the other line - RIDE's lnk6x against RTS6x - and is the default inside the editor; the compiler alone has no RTS6x option today.
  • Debug on x86_64-windows → clang → link.exe /DEBUG → cdb. Drawn above; the two configurations go through different assemblers and linkers on this target.
  • The prompted native retry: RIDE → Visual Studio's ml64 and link.exe, or TI's lnk6x, after one of RIDE's own tools failed and the user said yes. The console says building again with Visual Studio's ml64 and link.exe in place of the project's masm and link, as asked, and the build's output ends [built with Visual Studio's ml64 and link.exe, not RIDE's masm and link] - or [not built: ... failed as well].

How a build runs

A project build is one compiler command per group, in the order the project's "build" names them, and the link is one command after them. Inside a cpp11 command the files are compiled and assembled on cpp11's own pool of threads (one per file up to the machine's cores, one thread below four files, -j n to say otherwise); c90 and shalimar compile one file after another. A tms6747 group runs on RIDE's own pool: RIDE writes one -S -arch tms6747 command per source (toolchain.cpp, Recipe::commands) and runs them at once, one per source up to the machine's cores, each one's output written in source order (compile.cpp, runRecipe); one asm6x command then takes every .s, and one lnk6x command the objects. The editor itself runs a build on one worker thread, so the window keeps drawing; nothing else overlaps.
