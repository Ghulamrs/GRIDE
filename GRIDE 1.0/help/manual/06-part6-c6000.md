# Part VI — The C6000 target, the emulator, and real silicon

The fourth target, since 3.5, sets RIDE apart from 3.0. This part is the TMS320C6747
target end to end: what the compiler emits, how the emulator runs it without any
TI install, and how to produce a genuine chip binary with TI's tools.

--------------------------------------------------------------------------------
## 23. The TMS320C6747 / C6000 target

The TMS320C6747 is a C674x member of TI's C6000 family — a VLIW DSP: up to eight
functional units issue in parallel, instructions carry unit specifiers and `||`
parallel markers, and branches have delay slots. The compilers (`c90`,
`cpp11`, `shalimar`) generate C6000 assembly for `-arch tms6747` (`--target=tms6747`
for shalimar).

**The ABI, matched to TI's `cl6x`.** The backend implements the C6000 EABI as TI
does it, verified against `cl6x` output:

- Arguments in A4/B4/A6/B6/A8/B8/A10/B10/A12/B12, then the stack from B15+4;
  64-bit values in even:odd register pairs.
- A class of 8 bytes or less returned in A5:A4 and passed by value in a register
  or pair; a larger one through a hidden pointer in A4 (before `this`).
- Near (DP-relative, B14) data for scalars; the TI section conventions.
- 16-bit unsigned `wchar_t`, 32-bit `long`, 8-byte `long double`, 1-byte `bool`,
  `size_t` = `unsigned int`.
- TI's exception model: `.c6xabi.extab`/`.c6xabi.exidx`-style tables, the frame
  the unwinder expects, `__cxa_end_cleanup` at a cleanup pad — so a C++ exception
  thrown through our frames behaves as TI's does.
- Itanium C++ machinery (vtables, VTT, typeinfo, virtual thunks) laid out to
  match `cl6x` word-for-word, so our objects interoperate with TI-built ones.

The compiler emits the assembly TI's assembler accepts (`$` for the dots in
symbol names, `.ref` for undefined symbols, `EXTU`/`CLR` where an `AND` immediate
has no room, and the rest). Every emitted `.s` assembles under `cl6x`.

--------------------------------------------------------------------------------
## 24. The `vm6747` emulator

`vm6747.exe` is a C674x instruction-set simulator with just enough runtime to run
a compiled program and see what it computes — **no TI tools required, on any
host.** You hand it the assembly (and, for Shalimar, the runtime directory) and
it assembles the text in memory and executes it:

    vm6747 program.s                          (C or C++)
    vm6747 program.s bin\lib\shmrt-tms6747     (Shalimar: runtime beside it)

It provides the C6000 helper functions the code calls (`__c6xabi_div*`, the
64-bit shift/multiply helpers), a `printf`-class I/O path, `exit`, a heap, and
argc/argv. It is deliberately strict where that catches bugs (it faults an
unaligned load that silicon would allow) and it invents a few behaviours a real
board would define differently (division-by-zero faults; `abort` → 134; a fixed
16 MB heap; its own epoch for `time()`).

**What the emulator is for.** It is how tms6747 is a *first-class, trusted*
target and not a text-only backend: the same program's output is checked on the
emulator against the host targets, so a C, C++ or Shalimar program that computes
the right answer on x86-64 computes it on the C6000 too. In the editor, **Build ▸
Emulate on vm6747** on `tms6747` builds with `-S` and runs on `vm6747`, linking no
`.out`; F5 / Run project builds the TI program with asm6x and lnk6x against RTS6x
and runs the `.out` on `sim6747`. Either way the console shows the program's
output and `[program returned N]`.

**What the emulator is not.** It is not a debugger (the Debug menu turns tms6747
away by name), and it does not produce a file you flash to a chip — it runs the
assembly directly. Nor is it the toolchain's judge: it reads the assembly
*text*, so it never sees the bytes `asm6x` encoded or the image `lnk6x` laid
out, and it runs the program over **a C library and an exception-handling
runtime of its own**, not over RTS6x or TI's `rts6740`. A fault in the
assembler, the linker or the runtime runs clean on vm6747; it is **sim6747**,
running the linked `.out` with TI's boot code and the real runtime, that sees
them (section 25). Both have caught what the other could not, which is why
**Build ▸ Verify** runs a program on both and compares.

## 25. Real silicon: a `.out` from the editor, and the TI build path

**The editor's own way (since 2026-09-19).** `asm6x.exe` beside the editor is
the project's own C6000 assembler — ASM6x, a sibling of the MASM assembler,
held to TI's `asm6x` object for object on the compilers' whole tms6747 corpus.
With it there, every project build for `tms6747` turns the assembly in
`<program>.vm` into TI objects (`.obj` beside each `.s`), and the console says
`$ asm6x N sources`. A Shalimar program links its runtime packed beside RTS6x,
`shmrt6x.lib` or `shmrt6xd.lib` by configuration, ahead of `rts6x.lib` or
`rts6xd.lib`; with TI's runtime named under Tools its assembly is copied in under
`shmrt\` and assembled with the program instead.
**Then it links against RTS6x by default** (5.1): RIDE's own C6747 run-time
library, built from its own sources by cpp11 and asm6x and installed in
`bin\lib\rts6x-tms6747` in two builds: `rts6x.lib` at -O2 for a Release build and
`rts6xd.lib` at -O0 with `_DEBUG` for a Debug one, each with its `printf6x` library.
RIDE's `lnk6x` links the objects with the configuration's library
into `<program>.out` - `$ lnk6x N objects, rts6x.lib`, then
`[linked <program>.out]` - and nothing of Texas Instruments' is on the link
line. A CCS project's `libc.a` or `rts6740*` library is read as RTS6x's for the configuration;
its own `.cmd` file, heap and stack are kept. To link against TI's runtime
instead, name TI's C6000 compiler directory under **Tools > TI compiler for tms6747...**
(CCS's `ti-cgt-c6000_x.y.z`, the one with `bin\lnk6x`; and, asked for next, a
directory holding `rts6740_elf_eh.lib`, the exception-handling runtime CCS does
not ship — `ti-build` below can make one) and the same build goes on to
`lnk6x`, linking those objects against TI's runtime into `<program>.out`, the
file CCS loads onto a C6747; the console says `[linked <program>.out]`. A CCS
found on the machine and not named leaves RTS6x the runtime. On a
command line, `--ti dir [--tilib dir]` names them for one run. The emulator
still runs the assembly, as it always did; the `.out` is for the board. An
assembler that refuses or a link that fails is a failed build: what the
emulator runs must be a TI program, or the emulator is proving nothing.
`settings.json` keeps the two directories as `"ti"` and `"tilib"`.

**The project's own linkers (4.0).** Two more of the toolchain, written in
the same way as the assemblers and built beside the editor since 4.0 -
`lnk6x.exe` (LNK6x) for the C6747, held to TI's `lnk6x` byte for byte on its
probe bed, and `link.exe` (LINK) for Windows x86-64, held to Microsoft's
`link.exe` the same way. **Tools > Linker for tms6747...** names a linker to
use in place of TI's `lnk6x` for the `.out` (the runtime and the command
file are still TI's), and **Tools > Linker for x86_64-windows...** one in
place of Microsoft's for a Windows program; `--tilinker path` and `--linker
path` name them for one run, `-` in the console clears them, and
`settings.json` keeps them as `"tilinker"` and `"linker"` - and the installed
one names both (`bin/lnk6x.exe`, `bin/link.exe`): the project's own tools
are the tools by default. When one of them fails a build and the compilers
found no fault in the source, the editor asks whether to use the vendor's
for that build - TI's `lnk6x` under the directory Tools names, ml64 and
link.exe from the Visual Studio it found - and a Yes builds again through
them; `"askNative": false` never asks and lets the build fail. The question
is only put when the vendor's tools are on the machine; otherwise the line
says so. It is asked only when one of our own tools itself failed - a
program's own link error (an unresolved or duplicate symbol, a library made
for another platform) is refused by the vendor's tools the same way, so it
does not ask - and never for a `cl` build. When TI's `lnk6x` links a CCS
project whose `.cproject` leaves the memory model unsaid, RIDE passes
`--rom_model`, CCS's default: without it TI's linker takes no `_c_int00` from
the runtime and the `.out` has no entry point. Empty, and the build links as
it always did.

**The standalone script.** To produce a `.out` and Intel `.hex` for the real
chip from one source file, without the editor, RIDE also ships
`bin\ti\ti-build.cmd`. It is **license-safe**:
it contains and redistributes **none** of Texas Instruments' tools. It finds a TI
Code Generation Tools install already on the machine and uses it.

**Usage:**

    bin\ti\ti-build.cmd  path\to\program.c        (or .cpp, or .shl)

**What it does:**

1. **Finds the TI CGT**, in order: the `RIDE_TI_CGT` environment variable (the
   CGT folder), `cl6x` on `PATH`, or `C:\ti\ccs*\tools\compiler\ti-cgt-c6000_*`.
   If none is present it says so and points you to TI's free download — and notes
   the `vm6747` emulator still runs tms6747 without any TI install.
2. **Builds the exception-handling runtime once.** TI ships `rts6740_elf.lib`
   (no exceptions) and the means to build the EH variant. On first use, ti-build
   runs the CGT's own `mklib` to build `rts6740_elf_eh.lib` into a user cache
   (`%LOCALAPPDATA%\RIDE\tilib`), so nothing is written into the CGT install
   and nothing of TI's is shipped by us. (mklib needs a POSIX `sh`, such as Git
   for Windows provides, on `PATH`.)
3. **Compiles with our compiler** (`c90`/`cpp11`/`shalimar -S -arch tms6747`) to get
   the C6000 assembly.
4. **Assembles with `cl6x`**, links with `lnk6x` (against the EH runtime and, for
   Shalimar, the assembled `shmrt-tms6747` objects), using a flat-memory linker
   command file (`ti-link.cmd`), producing `program.out`.
5. **Converts with `hex6x`** to `program.hex` (Intel hex).

**Tested** across all three languages: C (a recursive `fib`), C++ (virtual +
`new`/`delete`), and Shalimar (with its runtime linked) — each produces a valid
C674x ELF `.out` (ELF magic, `e_machine` 140 = TMS320C6000, 32-bit, little-
endian, type EXEC) and a genuine Intel `.hex`.

**Is the output byte-identical to CCS's own?** **No.** Our compilers and TI's
`cl6x` are different compilers: different instruction selection, register
allocation and scheduling. So the objects, `.out` and `.hex` differ byte-for-byte
from a `cl6x`-compiled-from-source build (for the `fib` test: our `.out` 412,248
bytes vs `cl6x`'s 413,608; our `.hex` 103,840 vs 103,009). What *is* guaranteed —
and verified word-for-word — is **ABI / binary compatibility**: our objects link
against `cl6x`'s objects and TI's runtime, calling conventions match, and
vtables/typeinfo/exception tables match `cl6x`'s layout. That is why the TI link
succeeds and why a mixed program would interoperate; it is interoperability, not
identical machine code.

**When to use which:**

- **Run and test a tms6747 program** → the `vm6747` emulator (no TI tools, any
  host, shows the computed result).
- **Produce a real chip `.out`/`.hex`** → `bin\ti\ti-build.cmd` (needs a TI CGT
  on the machine; see `bin\ti\TI-BUILD.txt`).
