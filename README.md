# GRIDEx3

GRIDE in three outlooks - three IDEs for RIDE's toolchain, 3 in 1 - sharing one copy of that toolchain and one Help:

| Folder | What it is |
|---|---|
| `GRIDEd\` | **Black**, GRIDE 1.5.0 (GRIDEd) - C++/CLI, .NET Framework 4.8, multi-file; `GRIDE.sln` builds GRIDE and the eleven tools into `x64\<Config>\` |
| `GRIDE 2.0\` | **Grey**, GRIDE 2.0 - C++/CLI, .NET Framework 4.8, single translation unit; the same build into its own `x64\<Config>\` |
| `GRIDE 1.0\` | **White - The Simple**, GRIDE 1.0 - RIDE 4.7's window (C++/CLI over RIDE's portable C++ core in `src\`), renamed; the same build into its own `x64\<Config>\`. RIDE's console editor is left out. Since 2026-10-26 a Windows program of c90, cpp11 or shalimar is compiled to objects (`-c`) and linked by White itself with GRIDE's link - the compilers' own link would name Microsoft's runtime - on GRIDE's C runtime or Microsoft's (Tools > Windows C runtime, `settings.json` `windowsRuntime`), a Debug build with its PDB from the compilers' own CodeView; gride-dbg debugs it before cdb (Tools > Windows debugger, `windowsDebugger`), and F7 / F6 with nothing debugged stop at main's first line. A program's parts compile side by side, one per processor, the largest first (Tools > Parts compiled at once, `buildJobs`: `0`, the default; `1`, one part after another, as before), and are said in the project's order; the first part to fail stops those after it. cppparse's Release build takes 50 s instead of 113 s on 12 processors |
| `toolchain\` | the eleven tools the three solutions build (`..\toolchain\...`): c90, cpp11, shalimar, c2s (`Compilers\`), asm6x, lnk6x, rts6x, sim6747, vm6747 (`TI\`), masm, link (`Windows\`) - and beside them gride-dbg, GRIDE's Windows debugger (`Windows\DBG`), and grt, GRIDE's Windows C runtime (`Windows\RT`, into `lib\`), which the three solutions build too since 2026-10-26 (GRIDEd's since 2026-10-22) |
| `examples\` | the examples the three share, and the one folder the Setup installs as each outlook's `examples\`: `projects\` - cppparse (the latest, its repository's 77 files, `cppparse.sln` and a `.pro` built with cpp11), RIDE's C, C++ and Shalimar projects, the CCS samples, `cpp-sampleext` (the CCS sample SampleExt as a project for Windows, its sources unchanged), the showcase (three self-checking projects of several files) and the classic Shalimar set (eleven programs) - 29 `.pro` projects in the one format - `programs\`, RIDE's single files, and `toolchain-demo\`, the one copy of the demo that runs all eleven programs (it was in GRIDEd and GRIDE 2.0 each). The macOS package takes its `projects` and `programs` from here too |
| `docs\` | the Help the three share: `GRIDE_Help.html` (one brief page: the outlooks, the example, every outlook's keys, the versions, where things are), the reference pages and RIDE 5.17's manual; `GRIDE_Design_and_Development.html`, the project's report (2.0, 2026-10-27: the platforms, the languages, the GUI, the compiler toolchain with gride-dbg and grt, optimisation, development and verification, the open work; its diagrams are drawn by Mermaid from the web); `Runtime_Design.md`, the design of GRIDE's Windows runtime; each build copies it to `docs\` beside its GRIDE.exe |

This folder is a working copy of the local bare repository `My Documents\GIT Test\GRIDE` (no remote). GRIDEx2,
the two-outlook model, is that repository's tag `gridex2-1.1.0`; `My Documents\GRIDEx2` and the old folders
`My Documents\GRIDEd` and `My Documents\GRIDE` stay as they were then. Build one of the three solutions at a time:
their tool projects share the intermediate folders under `toolchain\` (situation W7 below).

**One project format, one settings file.** The three read and write one `.pro` format, White's (RIDE's): Black and
Grey read its `groups`, `include`, `libraries`, `arch` and `build`, and each outlook writes back the keys only another
keeps. Their settings are one file, `%APPDATA%\GRIDE\settings.json`, whose keys name GRIDE, never RIDE
(`GrideRoot`, `grideRoot`, keySet `gride`, the `GRIDE_*` variables); each outlook takes in its file from before
(Black's `gride.settings.json`, White's `%USERPROFILE%\GRIDE 1.0\settings.json`) the first time, and leaves the
others' keys as it read them.

None of the three needs `cmd.exe` to build or run a program. White's core went through cmd for every build (and
for vcvars64.bat); since GRIDEx3 it starts each program itself, taking RIDE's `cd ... && ...` lines apart, and finds
Visual Studio's tools, headers and libraries in the installation's own folders, as Black and Grey do (W10).
The compilers no longer need it either (2026-10-20): c90, cpp11 and shalimar, asked to assemble and link
themselves (`-c`, or straight to a program - how White builds), started masm and link through `std::system`, so
through cmd, and on a machine where cmd is disabled by policy every White build failed; they start a tool named by
its path directly now (CreateProcess), and only Visual Studio's bare-named `ml64` and `link` still go through
vcvars64.bat.

## Keeping GRIDEx2 working on Windows and the TMS targets

What GRIDEx2 depends on outside its own tree, what goes wrong when that is missing or different, and how to fix
it. This is a reference for later work: nothing here is required by an installer today, and the fixes are not yet
made unless the Status column says so.

### What it needs today

| Part | Needs on the machine |
|---|---|
| Building the solutions | Visual Studio 2022 or later with *Desktop development with C++*, *MSVC v143 - VS 2022 C++ x64/x86 build tools*, *C++/CLI support*, the .NET Framework 4.8 targeting pack and a Windows 10/11 SDK |
| `GRIDE.exe` (Release) | .NET Framework 4.8, and the VC++ 2015-2022 runtime: `VCRUNTIME140.dll` (both IDEs) and `MSVCP140.dll` (GRIDEd), which the installer ships beside the exe |
| The eleven tools (Release) | Windows only (static CRT, no other DLL) |
| Building for TMS320C6747 | nothing more: c90 / cpp11 / shalimar, asm6x, lnk6x, rts6x, sim6747 and vm6747 are all the toolchain's own |
| Building for Windows | nothing more with GRIDE's own runtime (`lib\grtstart.lib`, `grtcompat.lib`, `grtcxx.lib`, `grtc.lib`, `grtwin.lib` and its `kernel32.lib`, the default where there is no Visual Studio; docs\Runtime_Design.md): the program needs `kernel32.dll` alone, and a Debug build's PDB comes from GRIDE's `masm` and `link`. Microsoft's CRT, chosen under Tools > Options or taken automatically for a build with cl's objects, needs Visual Studio's MSVC libraries (`libcmt`, `libvcruntime`, `legacy_stdio_definitions`) and the Windows SDK's (`libucrt`, `kernel32`) |
| Debugging Windows programs | nothing more: `gride-dbg` over Windows' own `dbghelp.dll`; `cdb` (the Windows SDK's *Debugging Tools for Windows*) where it is chosen |

The TMS320C6747 target therefore keeps working on any Windows machine with the Release build, and since GRIDE's
own runtime (2026-10-23) so does the Windows target; only Microsoft's CRT, when chosen, leans on Visual Studio.
