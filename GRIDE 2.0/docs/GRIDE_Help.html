GRIDE 2.0 Help

C90 · C++11 · Shalimar — Windows · Linux · macOS · TMS6747 — RIDE's conventions

1. GRIDE 2.0 and its example

GRIDE 2.0 is a Visual Studio-style IDE for RIDE's toolchain: the C90, C++11 and Shalimar compilers, RIDE's assemblers and linkers, the TMS6747's emulator and simulator. It follows RIDE's conventions - its program names and command lines (read from toolchain.json), its build rules, its error shapes, its runs in the Output pane, its Compiler Options and settings, its debuggers - and reads Code Composer Studio 7.4 / 5.5 projects and Visual Studio solutions read-only. It holds one project at a time.

Its example is cppparse, the C++ project reader and compiler of the cpp repo, as a Visual Studio 2022 C++ solution:

  1. File > Open Project (Ctrl+Shift+O) and pick samples\cppparse\cppparse.pro. The title says cppparse [Visual Studio 2022 v143, read-only] - GRIDE 2.0; the Output pane says VS project cppparse: opened through cppparse.pro, which keeps GRIDE's compiler (cl), configuration and arguments for it.
  2. Ctrl+Shift+B builds it - Release or Debug from the toolbar's Config box, nothing to set under Tools > Options - with Visual Studio's cl and link.exe: $ cppparse (cl), [the project's own settings give cl: /W4 /WX /permissive- /EHsc /MT], $ linking with link.exe, [built ...\cppparse\.gride\out\Release\cppparse.exe].
  3. F5 builds and runs it in the Output pane: $ .gride\out\Release\cppparse.exe --health ., cppparse's health report on its own sources, then [program returned 0].

The Visual Studio files are only read; cppparse.pro keeps the compiler, the configuration and the arguments (section 3.6), and the build's objects and program go to .gride\ beside the .vcxproj.

3. RIDE's Express Help

GRIDE 2.0 drives RIDE's toolchain, so RIDE 5.17's Express Help is given here as RIDE wrote it (RIDE\packaging\windows\EXPRESS-HELP-5.17.md, as GRIDEd imported it). Where it describes RIDE's own window, menus or files, the note In GRIDE 2.0 under that part says what GRIDE 2.0 does instead. Its own cross-references (“section 7”) are RIDE's numbers: 3.7 here. The complete manual it points to ships as RIDE_Manual.html.

Three languages, four targets, one editor on three systems - a window on Windows and on macOS, a console editor on all three, and the project's own compilers, assemblers, linkers and C6000 emulator behind them. This is the quick reference; the full pages are under help/.

The suffix picks the language; the Language menu overrides it for a file whose name says otherwise. Each compiler announces itself on every compile (©2026 G. R. Akhtar - ISO C++ 11).

The four targets (Target menu, or Ctrl-T to cycle). A target the machine is not builds to assembly only (-S) and says so; tms6747 runs everywhere, on the emulator:

TargetRuns on
x86_64-windowsWindows
x86_64-linuxLinux
arm64-darwinmacOS (Apple silicon)

Shalimar assigns with :, never =: x : 2, int n : 5. = compares. Writing int x = 2 is answered Unexpected '=' use ':'.

In GRIDE 2.0: the suffix picks each file's language and colouring too, and the status bar shows it. The project's language (chosen in File > New Project) is the language of a new file. A build gives each file its compiler by its suffix while the project's compiler is auto; Project > Properties > Toolchain can name one compiler for every file instead (c90, cpp11, shalimar; a Visual Studio project's .pro can name cl, as the example's does), which refuses a file it does not compile with RIDE's sentence. The Target box on the toolbar picks the target, named Windows, Linux, macOS and TMS6747. A target this machine is not still builds to assembly only and says so (x86_64-linux only reaches -S here - switch to x86_64-windows to run it). On the TMS6747, Build and Run runs the linked .out on sim6747 and Debug > Emulate on vm6747 runs the assembly on the emulator (VM6747 / SIM6747). A Windows Debug build carries CodeView (clang and Microsoft's link.exe /DEBUG) and is debugged with cdb, or lldb where cdb is not installed. A Shalimar Debug program is debugged by its own session (SHM_DEBUG=1), which stops by statement; Locals says a Shalimar program says where it is, not what is in it.

3.3 Debug and Release: optimization

Build ▸ Configuration ▸ Debug / Release (Ctrl-D in the console editor) chooses how everything is compiled. The status bar shows which.

CompilerDebugRelease
c90, cpp11-g -D_DEBUG=1-O2 -DNDEBUG=1
host c++ group-g -D_DEBUG=1-O2 -DNDEBUG=1
cl group/Od /Zi/O2
shalimar--debug(no -O)
  • Debug is -O0 - no optimisation - and carries debug information.
  • Release optimises: cpp11 -O2 runs its optimizer (register allocation, copy propagation, loop alignment, inlining); for tms6747 it also schedules the C6000's instructions to their delay slots. -O1 and -O2 are the same passes today.
  • The choice belongs to the machine, not the project: it is kept in ~/.ride/state.json, and a "config" key in a .pro is ignored - a project that travels does not put everyone who opens it into Release.
  • On the command line: cpp11 -O2 prog.cpp -o prog (or -O1, or -O0, the default); c90 -O2 the same.

In GRIDE 2.0: the Config box on the toolbar chooses Debug or Release, and the status bar shows <target> | <configuration>. The choice belongs to the project, not the machine: a GRIDE project keeps it in its .pro (activeConfiguration), a CCS or Visual Studio project opened directly in GRIDE's settings.json, a Visual Studio project a .pro stands for in that .pro (the example's cppparse.pro says Release). The flags are RIDE's, from the Compiler Options table: Project > Compiler Options for the project, Tools > Options > Compiler Options for what a new project starts with; only what differs from RIDE's defaults is written into the .pro. cl takes its flags from toolchain.json (/Od /Zi /D_DEBUG, /O2 /DNDEBUG) and, for a Visual Studio project, the project's own settings after them - /W4 /WX /permissive- /EHsc with /MT for Release and /MTd /RTC1 for Debug in the example (section 1).

3.5 Making and building a project

Project menu: New…, Open…, Recent, Save As…, Close; New File, Add File (the one in front), Remove, Rename…, Delete…; Include Paths…, Libraries…. The file items act on the open project's files and are offered only while a project is open.

Build menu: Compile File (Ctrl-B), Run File (F5), Build Project (F4), Run Project, Stop, Clean (removes the program, its .pdb, .ilk, .out, .dSYM and .vm, and empties the panes - never a source or the .pro), Configuration ▸ Debug / Release, Convert C ⇄ Shalimar, Jump to Next Issue, Clear Issues.

The bottom panel shows Errors, Progress and Output. The title bar shows RIDE 5.17 - <project> - <file>, the status bar the language, the configuration, the compiler (* when the file chose it) and the target.

On macOS the menus are in the menu bar at the top of the screen and in a row inside the window; About RIDE is in the RIDE menu, as on every Mac app.

In GRIDE 2.0: GRIDE 2.0 holds one project at a time: File > New Project, Open Project (a .pro, a CCS project or a Visual Studio solution or project), Recent Projects, Close Project; Project > Add New File, Add Existing File, Remove from Project, Properties (include folders, libraries, defines and flags per configuration). Build > Build Project (Ctrl+Shift+B), Compile Current File (Ctrl+F7), Rebuild Project, Clean Project, Cancel Build; Debug > Build and Run (F5), Run Without Building (Ctrl+F5) and Stop (Shift+F5) - the program runs inside the Output pane, with an input line under it, to [program returned N]. Messages go to the Error List and the Output pane; the debugger's panes (Locals, Watch, Call Stack, Registers, Memory, Breakpoints) sit beside them. The title bar shows <project> - GRIDE 2.0 (cppparse [Visual Studio 2022 v143, read-only] - GRIDE 2.0 for the example), the status bar the file's language, its encoding and the target with the configuration. Tools > Convert C -> Shalimar and Convert Shalimar -> C run c2s. RIDE's debugger keys are GRIDE 2.0's: F8 debugs or carries on, F9 a breakpoint, F7 / F6 step over / into, Ctrl+Up / Ctrl+Down the stack; RIDE's Ctrl+B and F4 are Ctrl+F7 and Ctrl+Shift+B here (F4 is the Properties window).

3.6 The project file (.pro)

One JSON object; // comments are allowed.

{
  "name": "demo",
  "toolchain": "auto",           // auto | c90 | cpp11 | shalimar | c++ | cl
  "arch": "x86_64-windows",      // the target: one of the four
  "include": ["third_party/x/include"],      // extra header directories
  "libraries": ["third_party/x/libs/x.lib"], // extra objects and libraries
  "groups": {
    "Sources": ["main.c", "greet.c"],
    "Headers": ["greet.h"]
  },
  "build": { "target": "demo", "groups": ["Sources"] }
}
  • groups name the files shown in the left pane; a group may set its own "toolchain" (e.g. "c++" for the host's compiler).
  • build names the program the build makes (target - demo, or demo.exe on Windows) and which groups go into it.
  • Shalimar: every file has a main(); target names the file whose main() is the program, and a call to a function another project file defines is found there.
  • No build: nothing is built, and Ctrl-B still compiles the open file.

In GRIDE 2.0: GRIDE 2.0's .pro is its own JSON, not RIDE's: formatVersion, name, language, target, outputName, sourceFiles (relative to the .pro), includePaths, libraries, activeConfiguration, configurations (each with its defines, flags, link flags and output folder), and when they say something toolchain (the compiler word), emulateOnly, programArgs and options (RIDE's Compiler Options). It names one compiler for the whole project; RIDE's per-group "toolchain" has no counterpart. A CCS or Visual Studio project keeps its own files, which GRIDE 2.0 never writes: what GRIDE keeps for it - the configuration, the compiler word, the program's arguments, emulateOnly - is in settings.json, or, for a Visual Studio project, in a .pro whose visualStudio names it. The example's:

{
  "formatVersion": 2,
  "name": "cppparse",
  "activeConfiguration": "Release",
  "toolchain": "cl",
  "programArgs": [
    "--health",
    "."
  ],
  "visualStudio": "cppparse.sln"
}

3.7 A third-party library: include path and binaries

A library usually arrives as a header directory and prebuilt binaries. The project file carries the whole provision:

  • "include" - its header directories; every compile gets each as -I.
  • "libraries" - its binary files (.a / .o on macOS and Linux, .lib / .obj on Windows); each is handed to the link. Name each file.

Both lists are relative to the project, and Project ▸ Include Paths… / Libraries… edit them. Option ▸ Shared Include Paths… / Shared Libraries… hold the same two lists for every project, in settings.json.

thirdparty-mathx is the worked template: third_party/mathx/include, a libmathx.a built by clang for macOS and a mathx.lib built by Visual Studio for Windows. Open mathx-macos.pro on a Mac and mathx-windows.pro on Windows - they differ only in "arch" and the one library. A library made by another compiler links when its interface is C (extern "C"); one that passes std::string or std::vector across its interface does not, since RIDE's C++ library is its own.

In GRIDE 2.0: a project's include folders (includePaths) and libraries (libraries) are in its .pro, set under Project > Properties, with the defines and flags per configuration. The shared ones every project gets - include folders searched after the project's on every compile, libraries on every host link - are under Tools > Options > RIDE Paths. The rule about interfaces holds unchanged: GRIDE 2.0 builds with RIDE's compilers and RIDE's C++ library, except a Visual Studio project built with cl, which uses Microsoft's.

3.8 Windows: the assembler and clang

Inside RIDE, settings.json names masm as the x86_64-windows assembler, so RIDE builds need nothing from Microsoft to assemble. On the command line, cpp11 writes the GNU spelling by default, which clang assembles - the only spelling that lets a program of several C++ files share inline functions (COMDAT). cpp11 finds clang in any Visual Studio 2022 edition that has the C++ Clang tools component (Visual Studio Installer ▸ Individual components), in a standalone LLVM, or on PATH; with none, it assembles with masm instead and says so - enough for a one-file program.

To use masm yourself, ask for its spelling:

cpp11 -S -masm=masm hello.cpp -o hello.asm
masm -t x64 hello.asm -o hello.obj          (or masm /c /nologo /Fo hello.obj hello.asm)

A .s from plain cpp11 -S is clang's spelling and masm will not read it.

The link: link and lnk6x are RIDE's own. When one of them itself fails a build - not for the program's own link error, such as a missing main - RIDE asks whether to use Visual Studio's link.exe (or TI's lnk6x) for that build - found through vswhere or the directory Option ▸ Linker for tms6747… names; "askNative": false in settings.json never asks.

Real C674x silicon (.out / .hex): bin\ti\ti-build.cmd <program> builds a linked .out and Intel .hex with a Texas Instruments Code Generation Tools install already on the machine (none of TI's tools ship with RIDE); see bin\ti\TI-BUILD.txt.

In GRIDE 2.0: the same choices are made in toolchain.json, beside GRIDE.exe. A Windows Release build assembles with RIDE's masm and links with RIDE's link. A Windows Debug build writes the GNU spelling (-masm=gnu), which clang assembles, and Microsoft's link.exe /DEBUG writes the PDB; if clang or link.exe is missing, the build goes on with masm / link and says the debugger will see no lines. Files compiled by cl are Microsoft's objects, and Microsoft's link.exe links them in both configurations with the C runtime the objects name. Visual Studio's tools, INCLUDE, LIB and PATH are found without cmd.exe (vswhere, or the vcvars64.bat named under Tools > Options > RIDE Paths, whose folder is taken and never run). The native-tools question is RIDE's askNative, under Tools > Options > General. TI's C6000 compiler directory goes under Tools > Options > RIDE Paths.

It is made the first time RIDE starts, from the installation's own settings.json, which stays as the defaults: whatever yours does not set is read from there. In the Windows window, Tools ▸ Settings file... opens it.

What you were last doing - recent files and projects, Debug or Release - is in ~/.ride/state.json on every system.

In GRIDE 2.0: GRIDE 2.0 is built from GRIDE.sln; x64\<Config>\GRIDE.exe has beside it what every build copies there: toolchain.json, lib\ccs\ (TI's option definitions) and docs\ (this page and RIDE's manual). Your settings are %APPDATA%\GRIDE\settings.json, or a settings.json beside GRIDE.exe when one is there (a portable copy); every key of RIDE's settings.json has a place in them, on the RIDE Paths and Compiler Options pages of Tools > Options. Your toolchain overrides are %APPDATA%\GRIDE\toolchain.json (the one GRIDEd reads too) or toolchain.user.json beside GRIDE.exe. Recent projects and files are kept in settings.json, the configuration in the project (section 3.3).

3.10 Removing RIDE

  • Windows: Settings ▸ Apps ▸ RIDE ▸ Uninstall.
  • macOS: sudo rm -rf /Applications/RIDE.app /usr/local/ride, the links in /usr/local/bin (ride c90 cpp11 shalimar c2s vm6747 asm6x masm lnk6x), and sudo pkgutil --forget com.ghulamrs.ride.
  • Linux: /opt/ride/uninstall.sh (or <prefix>/uninstall.sh).

Documents/RIDE is yours and is never removed.

In GRIDE 2.0: GRIDE 2.0 has no installer: it is its folder and its settings.json. Removing it leaves RIDE installed, and removing RIDE leaves GRIDE 2.0, which then finds RIDE's programs only where toolchain.json and Tools > Options point.
