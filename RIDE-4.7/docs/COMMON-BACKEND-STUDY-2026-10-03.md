# Could MASM/LINK and ASM6x/LNK6x be the one common back end? A study, 2026-10-03

Read-only. Nothing was changed, committed, pushed or resealed. Every measurement below was
made today on this Mac, the Windows box (`ssh windows`, RIDE 4.7 as installed in
`C:\Program Files\RIDE 4.7`, CCS 5.5 and 7.4 under `C:\ti`) and the Linux box
(`ec2-user@52.202.164.123`, RIDE 4.7 under `~/ride-4.7`), with three small programs: a C
program (struct, switch, malloc, printf, `return 7`), a C++ program (virtual class, template,
`std::string` at file scope, `std::vector`, `try`/`catch` of `std::runtime_error`, `return 3`)
and `Compiler-Si/examples/factorial.shm`. The scratch files are not kept; the commands are
written out so they can be repeated.

## The answer in one paragraph

**Partly - and for the two platforms the question was first asked about, mostly already.**
On x86-64 Windows every compiler already emits MASM syntax, the installed RIDE 4.7 already
names `bin/masm.exe` and `bin/link.exe` in its settings.json, and today all three compilers'
output assembled with our MASM, linked with our LINK against Microsoft's static CRT, ran and
returned the right exit status on the box; the only thing the native tools still do is the
debug build, because MASM writes no line table and LINK no PDB. On the C6747 all three
compilers already go through ASM6x; LNK6x linked all three against `rts6740_elf_eh.lib` and
the images ran on TI's CCS 5.5 cycle-accurate simulator - but one of them wrongly (the C++
program's file-scope `std::string` was never constructed: LNK6x does not define
`__TI_INITARRAY_Base/_Limit`), and VM6747 cannot load a `.out` at all, so "one `.out` for the
board, the emulator and the simulator" needs an ELF loader in VM6747 before it is true. On
Linux and macOS we own nothing: the system `as`/`ld` (binutils 2.41 + glibc 2.34; clang's
integrated assembler + ld64 with ad-hoc signing) are the back end, and replacing them means
an ELF assembler and linker, a Mach-O assembler and linker, DWARF, dynamic linking against
glibc/libstdc++ and dyld, and code signing - a large project per platform that buys no
product capability, since those two hosts already have a free, measured oracle. So: make the
common back end official for Windows and the C6747, close the three measured gaps there, and
let the native assembler and linker stay the back end on Linux and macOS.

### 1.3 What the four tools of ours accept (from their sources, checked by the subagents' reads)

**MASM 1.0** (`MASM/README.md:62-90`, `src/x64_parse.cpp`): `.CODE/.DATA/.CONST/.DATA?`,
`SEGMENT` with `READONLY ALIGN(n) 'CODE'|'DATA'|'CONST'|'BSS'` and the extension
`COMDAT(sym)`/`ASSOCIATIVE(sym)` (`x64_parse.cpp:746-750`; `src/mscoff.cpp:141, :188-196`:
selection ANY or ASSOCIATIVE), `PROC [FRAME]`/`ENDP` with the seven unwind directives written
out as ml64 writes `.pdata`/`.xdata` (`:301-302, :615-660`), `OPTION PROC:PRIVATE|NOSCOPED|DOTNAME|CASEMAP`,
`PUBLIC/EXTERN/EXTERNDEF/COMM`, `DB..DQ/REAL4/REAL8/DUP/?`, `IMAGEREL`, `ALIGN`, `INCLUDELIB`
(`/DEFAULTLIB` in `.drectve`). Names may begin with `.` and hold `$ @ ? _`, so `.CRT$XCU`,
`.rdata$r`, `.pdata` and Microsoft-mangled names lex (`src/lexer.cpp:18-25`). **Refused**:
`PROC FRAME:handler` (`:500`), any other `OPTION`, AVX, any GNU/AT&T syntax, quoted names.
**No debug information at all** - no `.debug$S`, no CodeView (`README.md:153`). Oracle: ml64
14.44, 681 compiler-written files identical on bytes, relocations and symbols (`README.md:138-153`).

**LINK 1.0** (`LINK/src/main.cpp:80-150`, `src/layout.cpp`): COFF x86-64 objects and `.lib`
archives including import libraries (`src/archive.cpp:66-150`, IMPORT_NAME only); COMDAT
selections ANY/SAME_SIZE/EXACT_MATCH/LARGEST/ASSOCIATIVE (`layout.cpp:250-295`); relocations
ABSOLUTE, ADDR64, ADDR32, ADDR32NB, REL32..REL32_5, SECTION, SECREL (`:1064-1092`); `.pdata`
sorted (`:984-1003`); `/OPT:REF` and `/OPT:ICF` on by default; `/out /entry /subsystem /stack
/heap /libpath /defaultlib /nodefaultlib /include /base /map /timestamp`; `/DEBUG` accepted and
ignored with a warning. **Not implemented**: PDB/CodeView, DLLs/exports, delay-load, a TLS
directory (`.tls` is folded into `.data`), resources, `/FORCE`, `/DEF`, `/MERGE`
(`docs/known.md:105-119`). Oracle: link.exe 14.44, 38 corpus programs run identically, the 12
cpp11 COMDAT programs byte-identical (`tests/corpus/RESULTS-2026-09-23.md:48-54`).

**ASM6x 1.0** (`ASM6x/src/c6x.cpp:244-406`): `.text/.data/.sect/.bss/.usect/.global/.def/.ref/
.weak/.align/.word../.byte/.string/.float/.double/.space/.set/.asg/.symdepend`; `||` packets,
predication, the C64x+/C674x forms from TI's own asm6x (`src/forms.h`), compact 16-bit forms **on
by default** since 2026-10-03 (`src/main.cpp:14-30`); relocations ABS32/16/8, ABS_S16/L16/H16,
PCR_S21/S12/S10/S7, PREL31, EHTYPE (`src/asm.h:24-28`); `.c6xabi.exidx` as SHT_C6000_UNWIND
(`src/elf.cpp:60-72`). **No** DWARF/`--symdebug`, no SBR (DP-relative) relocations, no macros,
no `.field`. Oracle: TI asm6x 8.2.2; c90 403/403, cpp11 302/302, shalimar 58/58 byte-identical
objects (`README.md:193-198`).

**LNK6x 1.0** (`LNK6x/src/main.cpp:106-126`, `src/cmd.cpp`, `src/link.cpp`): TI ELF objects
and `!<arch>` libraries (`rts6740_elf_eh.lib`, 7.4.4's mklib build), `MEMORY`/`SECTIONS` with
`> RANGE`, `load=/run=/align=/fill=` and input lists (TI's `C6747.cmd` parses), `--rom_model/
--ram_model/--stack_size/--heap_size/--args/-e/--cgt=7.4.4|8.2.2`; `.cinit` with its own rle24
encoder; the unwind index composed and sorted with EXIDX_CANTUNWIND; far-call trampolines;
`.TI.symbol.alias`; SHF_GROUP first-copy-wins. **Not**: GROUP/UNION/PAGE/COPY/DSECT/expression
assignments in command files (`docs/known.md:290-292`), SBR relocations, `.clink`/`--retain`,
DWARF pass-through (non-ALLOC sections are dropped, `link.cpp:76-77`), a build-attribute check,
and - measured today - the `.init_array` bracket symbols (§2.5).

Three findings, in order of weight:

1. **LNK6x never defines `__TI_INITARRAY_Base` and `__TI_INITARRAY_Limit`**, so TI's startup
   runs no `.init_array` and the file-scope `std::string tag = "shapes"` is never constructed.
   `LNK6x/src/link.cpp:247-249` says so in its own words ("not here: the runtime declares them
   weak undefined and q07 shows lnk6x leaving them that way") - true of q07, which had no
   `.init_array`, and false the moment a C++ program has one. cpp11 writes the section at
   `backend/Tms6747.cpp:2246-2250`. Every program with a constructor at file scope, a static
   local of class type, or `std::cout` is affected. The kernels and the Compiler++ harness, which
   were cycle-identical to 7.4.4's images (`C++Optimize/CLAUDE.md:11139-11184, :11606`), do not
   exercise it, which is why it was not seen. **Small to fix** (two linker-defined symbols at the
   bounds of the `.init_array` output section, the shape `__TI_CINIT_Base/_Limit` already take
   at `link.cpp:255-259`), and it wants a case in LNK6x's probes and in `tests/c6747-three`.
2. **`args`, from both linkers**: TI's `_c_int00` gives `main` an `argc` of 0 unless the image
   carries an `.args` section (`--args=N`), where VM6747 passes `argc=1` (`Emulator/src/main.cpp:116-140`).
   A program that reads `argc` differs between the emulator and the simulator today; not a linker
   fault, but part of "one `.out` for all three" (§3).
3. **Not cycle-identical for the Shalimar image** (509,009 against 502,243, +1.3%) and +36 on
   the C one, where the kernels were identical: the DDR map, a 300 KB `.text`, and the
   `.cinit`/index differences `LNK6x/docs/known.md` lists are the suspects. Worth a probe; not a
   correctness fault.

### 2.6 VM6747 cannot run a `.out`

`vm6747 c.ti.out` → `vm6747: c.ti.out:1: unknown instruction '`. The emulator reads assembly
text only (`Emulator/src/main.cpp:1-3, :80`; `README.md:36-41`: it neither encodes nor decodes
C6000 machine words), calls `main` itself with its own stubs for the C library and the C++ ABI
(`src/Runtime.cpp:636-660`), models no CIO and no `C$$EXIT`, and uses a flat 32 MB map from 0
with text at 0x1000 (`Asm.h:12-16`) rather than the C6747's. The same `.s` files ran correctly
on it (`hi 10 4` exit 7, `shapes big 42 13.0`, factorial).

## 3. What would have to change, platform by platform

### 3.1 x86-64 Windows: MASM + LINK (ours exist, the gaps are debug and the fallback)

- **Syntax**: nothing. All three compilers already write MASM; cpp11 writes the COMDAT
  extension when told `-masm=masm`, which RIDE does (`toolchain.cpp:875-879`).
- **Object features**: COMDAT (376 of 384 sections in the C++ object) - MASM emits them, LINK
  folds them, ml64 cannot; `.pdata/.xdata` from `PROC FRAME` - written by MASM as ml64 writes
  them, sorted by LINK; the FH3 exception tables (`$cppxdata$`, funclets in `.text$x`) - plain
  data and code in MASM syntax, assembled and linked today (the C++ program throws and catches);
  `.CRT$XCU` for dynamic initialisation - a named segment, present in the object; `.rdata$r` RTTI
  - the same. **TLS**: LINK folds `.tls` into `.data` with no directory (`docs/known.md`) - none
  of the three compilers emits TLS, so it costs nothing today and would be a gap only when one
  does. **Debug**: MASM writes no `.debug$S` and LINK no PDB, so **a debug build cannot go
  through ours** - cpp11 already routes `-g` to clang and link.exe (Driver.cpp:926-928), c90
  refuses `-g` in MASM syntax, and RIDE's cdb needs a PDB. Closing that means CodeView `S_*`
  records and `.debug$S/$T` in MASM from a line directive the compilers do not yet emit, plus a
  PDB writer in LINK - **large**, and it is the one thing that keeps a native tool in the
  Windows loop.
- **Runtime libraries**: Microsoft's `libcmt/libcpmt/libucrt/libvcruntime/kernel32/legacy_stdio_definitions`
  and `shmrt-x86_64-windows.lib` link through LINK today (§2.2; `LINK/REVIEW-2026-09-20.md:13-22`).
  Nothing need be replaced. They need Visual Studio's `%LIB%` (RIDE's `vcvars` setting, `importMsvcEnvironment`),
  which is the one remaining dependence on an installed Visual Studio - for the *libraries*, not
  the tools. A redistributable set of those `.lib`s is a licensing question, not a technical one.
- **cpp11's `-masm=ml64` spelling** is dead weight: it no longer assembles with ml64 (§2.2) and,
  lacking COMDAT, cannot link a C++ program through our LINK either. Either mend or retire it.

### 3.2 TMS320C6747: ASM6x + LNK6x (ours exist; the gaps are the emulator, `.init_array`, and where the image runs)

- **Syntax**: nothing - every compiler's tms6747 corpus is ASM6x's own corpus, byte-identical to
  TI's asm6x (`ASM6x/README.md:193-198`). Two edges remain, both recorded: TI's asm6x pads so that
  no execute packet crosses a 32-byte fetch packet and ASM6x does not (`C++Optimize/CLAUDE.md:11279-11287`;
  the C674x permits the crossing and TI's simulator ran every kernel from ASM6x's objects), and
  ASM6x's README still says `.battr/.elfsym/.hidden` are accepted when the source refuses them -
  cl6x writes those, our compilers do not.
- **Object and image features**: unwind tables (`.c6xabi.exidx/.extab`, pr3 and pr2 for a function
  past 64 KB, PREL31 and EHTYPE) - written by ASM6x and composed by LNK6x, and `exception-table-large`
  runs on TI's simulator from an LNK6x image (`CLAUDE.md:11393-11405`); `.cinit` with rle24 - LNK6x's
  own, 7.4.4's coding (`CLAUDE.md:11305-11325`); far/near data - `.neardata/.far/.fardata` placed and
  `__TI_STATIC_BASE` defined, but **no SBR (DP-relative) relocations** in either ASM6x or LNK6x:
  our compilers never emit one (they address globals by `MVKL/MVKH`), TI's cl6x does at `-ml0`,
  so a cl6x object with DP-relative data cannot be linked by LNK6x. That matters only for a CCS
  project mixing cl6x objects, which RIDE's CCS import makes possible (`compile.cpp:671-706`).
  DWARF - none in ASM6x and dropped by LNK6x; TI's `--symdebug` has no counterpart, so CCS cannot
  source-debug our image. `.init_array` - **broken today (§2.5), small to fix**.
- **Runtime**: `rts6740_elf_eh.lib` is TI's, made once per box by `mklib` from CCS 5.5's 7.4.4
  (`CLAUDE.md:10944-10952`), and LNK6x links it (§2.5; the kernels, Compiler++). It cannot be
  shipped with RIDE - which is what `bin\ti\ti-build.cmd` and RIDE's `"ti"`/`"tilib"` settings
  exist for. Replacing it with our own C6000 runtime (startup, CIO, `malloc`, `printf`, the
  C++ ABI, the unwinder) would be the only way to a CCS-free `.out`, and is a large project the
  emulator's native stubs do not shortcut, since those run on the host.
- **Where the image runs** is the real work, and it is in VM6747, not in the linker: an ELF
  loader (program headers into the flat memory), a model of TI's startup or at least the entry
  point and `C$$EXIT`, CIO (`.cio` buffer protocol, which is what `printf` becomes in TI's
  runtime), the C6747 memory map instead of a flat 32 MB, and decoding of machine words - the
  emulator today executes *text* and has no decoder (`README.md:36-41`). **Large**. Until then
  "runnable through ASM6x/LNK6x" means TI's simulator and the board, and the emulator runs the
  `.s`, as RIDE does now.

### 3.3 x86-64 Linux: we own nothing, and would need everything

- **Assembler**: an ELF x86-64 writer taking GNU/AT&T syntax with `.cfi_*` (into `.eh_frame`),
  `.section` with flags and `@progbits/@init_array`, `.weak/.hidden/.comm`, `@GOTPCREL`/`@PLT`
  relocations (`R_X86_64_PC32, PLT32, GOTPCRELX, 64, 32S`), `.gcc_except_table`, `.debug_*`
  for `-g`. MASM's instruction encoder (`x64_encode.cpp`, verified against ml64 on 30,923
  instructions) is reusable; the parser is not (MASM accepts no AT&T), nor the COFF writer. Call
  it a third of a MASM - **medium** - unless the compilers were switched to Intel-syntax ELF, which
  is its own change to three backends.
- **Linker**: an ELF linker against glibc as a *shared* library: `crt1.o/crti.o/crtbegin.o`,
  dynamic section, `.interp`, PLT/GOT, symbol versioning (`GLIBC_2.34`), `R_X86_64_*` relocations,
  `.eh_frame_hdr`, `.init_array` merge, `__dso_handle`, `.data.rel.ro` and `-pie` on boxes that
  default to it - or a fully static link against libc.a/libstdc++.a, which is simpler but makes
  the C++ runtime 2 MB per program and is not what the oracle builds. **Large.** LINK's layout
  code is PE-shaped (COFF sections, base relocations, import tables) and shares little.
- **Runtime**: glibc, libstdc++ (`__cxa_*`, `operator new`, the Itanium unwinder in `libgcc_s`)
  are the system's and would stay; only the tools would change.
- **What it buys**: nothing measurable. The native `as`/`ld` are free, installed, and the oracle
  the suites already compare against (`run.sh` 545/0, `names.sh` against clang). It would remove
  a working oracle and add a second implementation to keep level with it.

### 3.4 macOS arm64: the same, plus signing

- **Assembler**: an arm64 encoder (none exists in the product - MASM is x86-64 only, ASM6x is
  C6000), Mach-O writer, `.cfi_*` into `__eh_frame` or compact unwind, `__TEXT/__DATA` sections,
  `.subsections_via_symbols`, `.weak_def_can_be_hidden`, `@PAGE/@PAGEOFF/@GOTPAGE` relocations
  (`ARM64_RELOC_PAGE21, PAGEOFF12, GOT_LOAD_*, BRANCH26, UNSIGNED, SUBTRACTOR`). **Large** - a
  new ISA encoder plus a new object format.
- **Linker**: Mach-O linker: `LC_DYLD_INFO`/chained fixups, binding to `libSystem.B` and `libc++.1`
  by install name, `__stub`/`__got`, `LC_MAIN`, `LC_CODE_SIGNATURE` with an **ad-hoc SHA-256 code
  directory** - arm64 macOS refuses an unsigned binary, so a linker that cannot sign produces
  nothing that runs (ld64's `linker-signed` flag, §2.4). `dsymutil` for debug. **Large.**
- **What it buys**: nothing; clang's assembler and ld64 are the oracle and ship with Xcode, and
  the arm64 optimizer work is deferred anyway (memory: arm64-optimizer-deferred).

| Windows | cpp11 | `-masm=ml64` spelling fails ml64 (A2015) and cannot link through LINK (no COMDAT) | small (retire) / medium (mend) | - |
| Windows | all three | Microsoft `.lib`s come from an installed Visual Studio (`%LIB%`) | small, licensing not code | a machine with no VS cannot link, with either linker |

## 5. Recommendation and order of work

**Per platform:**

- **Windows x86-64: yes, ours end to end** - it is already the installed default for all three
  compilers and ran today; make it official, keep ml64/link.exe only for the debug configuration
  and the "ask native" fallback, and stop treating `-masm=ml64` as a supported spelling.
- **TMS320C6747: yes for the toolchain, not yet for the emulator** - ASM6x + LNK6x against TI's
  `rts6740_elf_eh.lib` is the measured path to the simulator and the board; fix `.init_array`
  first; VM6747 stays an assembly-text emulator until it grows an ELF loader, and RIDE should
  say which of the two it ran.
- **Linux x86-64: no - the system `as`/`ld` stay.** Nothing in the product needs an ELF toolchain
  of its own, and the native one is the oracle.
- **macOS arm64: no - clang's assembler and ld64 stay**, for the same reason plus code signing.

**The one "common back end" configuration in RIDE** is then the settings.json already shipped,
made explicit and complete:

```json
"assembler": "bin/masm.exe",     "linker": "bin/link.exe",          // x86_64-windows
"tilinker": "bin/lnk6x.exe",     "ti": "<CCS cgt dir>", "tilib": "<dir with rts6740_elf_eh.lib>",  // tms6747
"askNative": true,               // ml64/link.exe or TI's lnk6x by consent, on our failure
"backend": "ours"                // new: "ours" | "native"; "ours" is the default and what Tools > Toolchain shows
```

with `-g`/debug documented as the one configuration that takes clang and link.exe (until MASM
writes CodeView), and the tms6747 run target offering "emulator (.s)" and "simulator (.out)"
once a CCS directory is named. No new switch is needed for Linux or macOS; they have no
"ours".

**Order of work:**

1. **LNK6x: define `__TI_INITARRAY_Base/_Limit`** (and a probe with a C++ static constructor,
   run through `tools/c6747-three`). Small; it is a wrong answer today on every C++ program with
   dynamic initialisation linked by LNK6x.
2. **Make the Windows common back end the stated default everywhere**: c90 and shalimar choose
   `masm.exe`/`link.exe` beside them as cpp11 does (Driver.cpp:926-928 is the model), retire or
   mend `-masm=ml64`, and add a `tests/winlink`-style suite that builds the three compilers' suites
   through masm + link and runs them on the box (the three-box rule's Windows leg, with link.exe's
   images as the byte oracle LINK already uses).
3. **VM6747 ELF loader** (program headers, entry at `_c_int00` or at `main` with TI's
   `__TI_cinit_table` applied, CIO `.cio` buffer, `C$$EXIT`, `--args`), so one `.out` runs on the
   emulator, TI's CCS 5.5 simulator and the board, and `tests/tms6747.sh` can gain a `.out` lane
   compared against the simulator's cycle counts the way `c6747-three` already compares cl6x's.
   Large, and the one piece that makes the C6747 claim whole.
4. **RIDE**: a `backend` setting, a Tools dialog that shows which assembler/linker each target
   will use, the `.out` run target, and a console line naming the tools that ran - today a build
   says `$ asm6x` and `$ lnk6x` but a `.out` is made and never run.
5. **Debug on Windows through ours**: CodeView line records in MASM from a `.line`-style directive
   the compilers would emit in MASM syntax, and a PDB writer in LINK. Large; do it last, and only
   if a VS-free Windows debug build is wanted - until then clang + link.exe for `-g` is honest
   and measured.

Not recommended: an ELF or Mach-O assembler and linker of our own. They would replace a free
oracle with a second implementation on two platforms where the product gains no capability.

**How to verify any of it**: the suites through ours (`tests/run.sh`, `emit.sh` with its golden
unchanged at `-O0`, the Windows cases through masm + link, `tests/winlink` both ways against
cl), the three-box rule (`tools/verify-three` with a `windows` leg that names `bin\masm.exe` and
`bin\link.exe` and a `c6747` leg that links with `bin\lnk6x.exe`), and TI's C6747 simulator as
the oracle for every `.out` - output, `C$$EXIT`, and `cycle.Total` equal on the Windows and
Linux CCS 5.5 boxes, as `tools/c6747-three` already measures. Each run under 30 minutes and one
DSS session at a time on the Linux box.
