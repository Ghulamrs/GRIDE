# RIDE 3.5 audit, 2026-09-19: projects, the menus, and the three files

Subject: RIDE at `eff2616`, both front ends - the console editor (`src/`, driven by
`tests/session`) and the Windows window (`winforms/MainForm.h` over `winforms/bridge.cpp`),
which share `src/project.cpp`, `src/workspace.cpp`, `src/settings.cpp` and `src/compile.cpp`.
Method: every line of the project, workspace, settings and menu code read; every item of every
console menu driven by keystrokes in two states (no project; inside a project with a C file) by
a probe built on the session harness, its status line recorded; the project flows (New, New
File, Add, Remove, Save, Target, Tools, Quit) driven end to end and the `.pro` read back; the
window's handlers read and matched to its menu wiring, not run. Mac only, by instruction. The
existing suites pass first: `tests/test` 1031/0 and `tests/session` 325/0 (the one failure
`make test` shows is the harness naming the compilers relatively - F14 below).

Findings are numbered **F1-F18**, severity **A** (a project cannot be built, or work is lost),
**B** (a wrong or misleading result), **C** (duplicate, dead or inconsistent surface), **D**
(documentation disagrees with the code). Nothing was changed; the ledger at the end says what
each would take.

--------------------------------------------------------------------------------
## 1. The three files, and what belongs in each

RIDE keeps state in three places, and the split is sound where it is followed:

| file | one per | holds | written by |
|---|---|---|---|
| `<dir>/<name>.pro` | project | `name`, `toolchain`, `arch`, `indent`/`tabs` (only if said), `groups` (files, and a per-group `toolchain`), `include`, `libraries`, `open`, `build{target, groups}` | every add/remove/rename/delete/regroup (`workspace.cpp`'s `andSave`), Project > Save / Save as, and `open` on Project > Close and File > Quit |
| `<install>/settings.json` (one above `bin\`) | installation | `include`, `lib` (where the shipped headers are), `vcvars`, `assembler`, `ti`, `tilib`, `compiler` (the default Tools choice), `indent`, `tabs`, `font`, `includes`, `libraries` | Tools > Header directories / Include paths / Libraries / Locate vcvars / Assembler / TI compiler / Font, and *every* Tools > compiler choice |
| `~/.ride/config.json` | user | `project` (last), `recent` (3), `files` (3), `config` (debug/release), `plain`, `font` (fallback) | opening a project or file, Ctrl-D, Plain frame, Font |

**The rationale, as the manual (Part III §11) states it and the code mostly keeps:** the `.pro`
says *what the program is made of* and where it opens; the installation file says *where the
tools and shared headers are*; the user file says *what this person was doing last*. Three
places where each fact has one owner. The audit found four facts with two owners or none:

- **F1 (D/B). The Target menu does not write `arch` to the `.pro`.** The manual: "The editor's
  Target menu changes it." The code: `Project::setArch()` is never called by either front end
  (`grep setArch src winforms`: only the declaration). `applyProject()` reads `arch` on open;
  Target > tms6747 changes `arch_` for the session, and Project > Save then writes the *old*
  value back, since `save()` writes `arch_` of the Project object, which nobody updated. Driven:
  a `.pro` with `"arch": "x86_64-linux"`, the target moved to arm64-darwin (the status line
  confirms it), Tools > cxx1 (confirmed), Project > Save - the file is rewritten and still says
  `"arch": "x86_64-linux"`, `"toolchain": "auto"`. A project cannot be made to remember its
  target or compiler from inside the editor at all; only by editing the file.
- **F2 (D/B). The Tools menu writes the installation's default, never the project's `toolchain`.**
  Every Tools > cc1/cxx1/shc/cl/C++ choice calls `settings::rememberDefaultCompiler()` and writes
  `compiler` into `settings.json` - for every project on the machine from then on - while the
  `.pro`'s own `toolchain` stays `auto` (`setToolchain()` is called only from `main.cpp`'s
  `--toolchain`). Ctrl-K, which cycles the compiler, therefore silently rewrites an
  installation-wide setting. The manual says of `compiler`: "choosing one from the Tools menu
  writes it here" - that part is documented - but a person inside a project reasonably expects
  the choice to be the project's, and there is no way to make it so from the menus.
- **F3 (C). Tools > "Include paths..." and "Libraries..." edit the installation's lists, and the
  project's `include`/`libraries` have no editor at all.** In both front ends the two items
  prompt for `settings::includes()`/`libraries()` and write `settings.json`; the bridge has
  `ride_project_set_includes/libraries` (writing the `.pro`) and the window never calls them.
  The action names in `menu.h` are `ActionProjectIncludes`/`ActionProjectLibraries`, which is what
  they were meant to be. The manual documents both lists correctly, and says the project's are
  "searched first" - true in `compile.cpp` - but a project's list can only be typed into the file.
- **F4 (B). `.pro` and the old `.json` project file are named interchangeably in messages.** `Project::fileName()`
  still returns the old `.json` name (the format's old name; `ed1.json` before that), and
  `beginProject`/`beginFromWhatIsThere`/`targetParts` build their messages from it: Project > New
  says *"the old .json project file written - Shm"* when the file written is `Shm.pro`; a build refused for want
  of a `build` entry says to add it "to the old .json project file"; a directory opened with no project says "no
  the old .json project file here, so one was made". `load()` still reads a legacy `.json` project file (under either old name)
  (right), but `fileName()` should not name what is written.

The debug/release configuration lives in the user file, not the project - the manual says so
("an editor toggle, not a `.pro` field") and the code agrees. Two projects that need different
configurations therefore share one switch; that is a decision, recorded here and not counted.

## 2. Project creation, and adding, saving, removing and deleting files

Every operation goes through `workspace.cpp`, one function each, and every one that changes the
project saves the `.pro` on the spot (`andSave`). That is the right shape: the file on disk never
lags the pane. The findings are about what the front ends let a person reach, and one rule that
the language models do not share.

**Project > New.** Console: prompts for a name, makes `<name>.pro` in `projectDir_` - the
directory of the project already open, or `.` - with one group `Sources`, `build` naming it, and
the current buffer's file added if it has one. Window: a folder picker, then the name. Findings:
- **F5 (B).** With a project open, New puts the second `.pro` beside the first without a word,
  and the first is replaced in memory without Close - the message "2 projects here, Project >
  Open chooses" appears only on the next open. The window asks for a folder; the console cannot.
- F4 applies (the message names the old .json project file).

**Project > Open.** Console: a picker walking directories, offering `*.pro` files and `./`;
the window: a file dialog. A directory with no project gets one made from what is there
(`beginFromWhatIsThere`): `.c/.cpp/.cc/.s` to `Sources`, `.h/.hpp` to `Headers`, `.shl` to
`Shalimar`, one level of subdirectories. Finding F9 (below) applies: a directory of Shalimar
files gets a project that builds nothing.

**Project > Save / Save as.** Save rewrites the file the project already keeps current, so it is
only ever needed after F1/F2 - and then it writes the unchanged values. Save as names another
file *in the same directory* (`path::join(project_.root(), name)`), so it cannot move a
project. **F6 (C):** Save is a no-op in every reachable state; it exists for a file the editor
keeps saved, and its one useful case (after a Target change) does not work (F1).

**Project > Close.** Closes the project's open documents (refusing if any is dirty), records
`open`, clears the pane. Correct, and the session suite covers it.

**Project > New File.** Prompts for a name; the extension is added from the Tools choice or the
project's majority language; the file is made on disk, added to the group its extension names,
and opened. Correct for C and C++. **F9 (A)** for Shalimar - see §4.

**Project > Add File.** Console: adds *the current buffer's file*, no picker - to add a file one
must open it first. Window: an Open dialog, then the group. **F7 (C):** the two differ, and the
console's item cannot add a file that is not already in front.

**Project > Remove File.** Both front ends: removes the current buffer's file from the project,
leaving it on disk. Correct. Note that Rename and Delete (below) act on the *tree selection or
the buffer* (`targetFile()`), while Remove and Add act on the buffer only - three different
answers to "which file".

**Rename, Delete, Move to group.** Implemented in full in the core (`renameFile`, `deleteFile`,
`moveToGroup`: the project follows the file, breakpoints follow a rename, open buffers are
re-pathed, delete asks for "yes"), with actions `ActionFileRename/Delete/Regroup` and console
handlers `Editor::renameFile/deleteFile/regroupFile`, and window handlers
`OnRenameFile/OnDeleteFile/OnMoveToGroup`. **F8 (A): none of the three is reachable from either
front end.** The console's `Menu()` has no item carrying the three actions and `processKey` maps
no key to them (the tree pane answers only Enter); the window defines the three handlers and
attaches them to nothing (`grep OnRenameFile winforms`: the definition alone). A file can be
renamed or deleted only outside the editor, after which the project lists a file "not on disk"
and refuses to build. The manual's key table and menu list do not mention them either, so the
loss is invisible.

**Quit.** File > Quit (menu) records the front file as `open` in the `.pro`; **Ctrl-Q does not**
(`case ctrl('q')` in `processKey` sets `running_ = false` without `rememberOpen`), so the same
command behaves differently by the route taken - **F10 (B)**. The window's Exit goes through one
path.

**F15 (B).** Every Target item, with Tools on "By language" and a `.c` in front, answers *"target
is a cc1, cxx1 or shc setting - auto builds for its own host"* - false on both counts. The test
is `usesArch(tool_.kind)` with `kind == ToolAuto`; it should resolve the kind for the file in
front (`resolve(tool_, lang_)`), which is c90 here and does take `-arch`. The target *is*
changed; only the message denies it.

**F16 (C).** The console menu reopens on the column last used (`Menu::close()` clears `item_`
and not `column_`), so F10 lands on Project after a Project action and on Debug after a Debug
action - a keystroke sequence that opens "File > New" once opens something else the next time.
Deliberate or not, it is undocumented, and the letter keys do not rescue it because
**"T" reaches Tools and never Target** (`Menu::key` takes the first title starting with the
letter). Every other column has a letter of its own.

**F13 (C). The two front ends disagree on nine keys** - Close (Ctrl-W vs none), Select all
(Ctrl-A vs none), Re-indent (Ctrl-L vs Ctrl-A), Line numbers (none vs Ctrl-L), Find next/
previous (F3/Shift-F3 vs Ctrl-G/none), Replace (Ctrl-H vs Ctrl-R), Next/previous file
(Ctrl-PageDown/Up vs F3/F2), New File (Ctrl-N vs none), next pane (none vs Ctrl-W). The manual
says the window "differs deliberately on ten keys" and names two of them; the rest is left to be
discovered. Ctrl-W and Ctrl-L mean different things in the two - the pair most worth reconciling.

**F14 (C).** `make test` fails one check ("and the two compile and link into one program") when
`CC1`/`CXX1` are given relatively (`bin/c90.exe`), as the Makefile's own `check` target invites;
`buildParts` runs the compilers from the objects directory, where a relative name resolves to
nothing. Absolute paths pass 1031/1031. Either the Makefile should absolutise or the harness
should say why.

## 4. Do the language models synchronize?

Three choices describe "what this is": the **Language** menu (`langChoice_`: colouring and the
indent dialect, per session, never saved), the **Tools** menu (`tool_.kind`: which compiler,
saved to the installation - F2), and the **file's extension**, which is what the *build* goes
by: `Project::targetParts` sorts a group's files by `languageOf()` and hands each language to the
compiler `resolve()` names, or to the group's own `toolchain` if the `.pro` says one. The
per-group toolchain has no UI (`setGroupToolchain` is called from nowhere; the manual documents
the file form only). Shalimar is then held to its own rules - one program per project, one
compilation, no mixing with C in a group - and those rules are enforced with good messages
(`targetParts`, `oneShalimarProgram`), and the session suite covers them.

What does not synchronize is the **group model**, and it breaks Shalimar projects made in the
editor:

- **F9 (A). A Shalimar project made through the menus cannot be built.** `groupForNamed()` sends
  `.shl` to a group called **Shalimar** (and headers to **Headers**, C/C++ to **Sources**); a new
  project's `build` entry names **Sources** alone; nothing ever adds Shalimar to it. Driven, in
  a fresh directory: Project > New "Proj", Project > New File "prog.shl", type a `main`, Ctrl-S,
  F4 - *"the groups this project builds from hold no source"*, and the `.pro` reads
  `"groups": {"Sources": [], "Shalimar": ["prog.shl"]}, "build": {"groups": ["Sources"]}`. The
  same steps with `prog.c` or `prog.cpp` build. Add File and a directory opened without a project
  (`beginFromWhatIsThere`) take the same path, so every way of getting a `.shl` into a new
  project ends outside the build. The session suite's "a project made of Shalimar" writes its
  `.pro` by hand with the `.shl` in Sources, which is why it is green. The window shares
  `workspace.cpp` and so the fault.
- **F17 (C).** `.shm` - the spelling every case of `Compiler-Si/tests` and its examples use, and
  one shalimar itself accepts - is Plain text to the editor everywhere (`languageOf`, `languageFor`,
  `groupForNamed`, `withExtension`): no colouring, no compiler, not built. `.shl` has been the
  editor's spelling since 2026-08-27 by decision; the decision should either be enforced in
  Compiler-Si's tree or `.shm` taken as a second spelling, since a person who opens the
  compiler's own examples in RIDE gets text.
- **F18 (C).** `languageOf` (project.cpp) takes `.cxx`; `groupForNamed` (workspace.cpp) and
  `languageFor` (syntax.cpp) do not - two lists of "what is C++" that drifted.

Otherwise the models meet correctly at the build: a group with C and C++ splits by extension
and links; a Shalimar group refuses a C file with the right message; `tms6747` refuses libraries;
the emulated target's runtime rules for Shalimar are in one place (`launchCommand`,
`makeTiProgram`). The chain the manual describes - Language is what the file *is*, Tools which
compiler reads it, Target which machine - holds for the *file in front* (Ctrl-B, F5); for the
*project* (F4) only the extension and the `.pro` speak, and neither menu reaches the `.pro`
(F1, F2).

## 6. Mended, 2026-09-19 (same day)

At the user's word, F9, F8, F1, F2 and F10 were mended, and F4 with them since the new
session case reads the message. In the core and both front ends:

- **F9**: `groupForNamed` sends `.shl` (and `.cxx`) to Sources - the group a project made here
  builds - instead of a group of its own; the build's own rule still refuses Shalimar and C in
  one group, with its message, when that is what someone puts there. A `.shl` made by Project >
  New File now builds with F4 (`tests/session`: "the audit's mends").
- **F8**: Rename File..., Delete File... and Move to Group... are on the Project menu of both
  front ends, after Remove File, wired to the handlers that were already there.
- **F1, F2**: `Editor::chooseArch` / `chooseTool` in the console and `OnTarget` / `ChooseTool` in
  the window write the choice to the open project's `.pro` (new bridge calls
  `ride_project_set_arch` / `ride_project_set_toolchain`), and to the installation's
  `compiler` only when no project is open; the status line says which file was written. The
  Target message no longer claims "auto builds for its own host" (F15 went with it).
- **F10**: Ctrl-Q is `perform(ActionQuit)`, so the front file is remembered either way; and a
  file removed or deleted from the project is cleared from `open`, which the session suite's
  Remove File case then caught depending on.
- **F4**: the messages name the `.pro` that was written; `Project::fileName()` stays for reading
  the legacy the old `.json` project file.

Two things the box then showed, mended too: the unit suite's "configuration defaults to
debug" read the live `~/.ride/config.json` and had failed there since Release was
selected, which stopped `build.bat check` before it recompiled `session.exe` - so the box had
been running a session harness from 09-16, and the two-file Shalimar case added at `eff2616`
had never run there. Rebuilt, it failed: on Windows the emulated Shalimar program's assembly
was named `prog.exe.s` (`.exe` from the program name), where the harness and the `.vm`
directory say `prog.s`. Both are fixed: the check reads a disposable home, and the assembly
is named after the program without its `.exe`, on every host.

Mac: `tests/test` 1035/0, `tests/session` 337/0 (12 new checks). Windows box, RIDE's default:
the solution with the window built (`RIDE.exe`), `tests/test` 924/0, `tests/session` 301/0
with the new case.
