1Introduction

1.1Purpose

This report records how GRIDE is designed and how it is built and verified. It is written for engineers who maintain or extend GRIDE and for reviewers who need its scope, its standards and its limits in one place.

1.2Scope

  • The GUI: GRIDE, version 1.5.0.0: editor, projects and workspaces, build, run and debug.
  • The whole toolchain GRIDE drives: c90, cpp11, shalimar, asm6x, lnk6x, RTS6x with ar6x, sim6747, vm6747, masm and link.
  • Four targets: 1. x86_64-windows and 2. tms6747 (the TI TMS320C6747 DSP), the two complete ones; 3. x86_64-linux and 4. arm64-darwin, reached as far as assembly.

1.3Baseline

Facts are taken from the GRIDE repository at commit 0270f68 (2026-10-21) and from the work in progress on top of it: cpp11 1.25, the C6747 variables under -g, and Setup 1.4.0. Where the old RIDE 5.17 manual and the source disagree, the source is followed.

Draft 0.1 gives the structure and the key facts of every section. The detailed version (10–15 pages) will expand sections 4–8 and add the findings of the independent cpp11 conformance review now in progress.

2System overview

GRIDE is a Windows IDE built around its own compiler toolchain. The GUI holds the editor, projects and workspaces, the build, the run and the debugger. Every tool it starts, and every switch it passes, is defined in toolchain.json, so the GUI itself names no tool. Projects are .pro files, the settings live in one settings.json, and the Help is a set of HTML pages beside the program.

5The GUI: GRIDE

GRIDE's GUI is layered, so that each part can be read, tested and replaced on its own. Its class map and main flows are documented in the source tree's ARCHITECTURE.md.

5.1Layers

Each layer uses only the layers above it in this table.

LayerHolds
CoreJSON reader and writer, paths, languages and targets, Win32 calls (job objects, pseudo-consoles)
ModelProjects (.pro), workspaces (.grws), build configurations, the CCS 7.4/5.5 and Visual Studio readers
SettingsThe settings file, toolchain.json and its definitions (tools, sessions, libraries, targets), compiler options
ServicesTool lookup, the build engine, macro expansion, tool and program runners, Visual Studio discovery, diagnostics, the debug engines
UIThe main form, commands and key sets, the editor, docking, panes, dialogs, themes

5.2How a build runs

  1. The main form starts the build engine on a worker thread.
  2. For each project: for each source, the compiler is chosen (the group's word, else the project's, else the language's), and its command line is built from toolchain.json, each $(…) placeholder filled in.
  3. The objects are linked: masm and link on Windows, asm6x and lnk6x with RTS6x on the C6747. If the toolchain's own assembler or linker fails, the user is offered the native tools.
  4. Each tool is started directly in a job object. cmd.exe is used only when the user configures a setup script.
  5. Output, messages and the finish event return to the Output pane and Error List.

5.3How debugging runs

F5 builds, then picks an engine for the target: cdb for Windows (lldb as fallback), sim6747 or vm6747 for the C6747, and the Shalimar runtime's own session. One driver sends one command at a time, ended by a marker, over pipes or a pseudo-console, and reads the gdb-, lldb- or cdb-shaped answers back into the panes.

5.4Shared files

  • .pro: JSON with comments. Its keys (name, toolchain, arch, groups, include, libraries, build …) name the sources and their groups, the target and what the build makes; a key GRIDE does not know is kept when it saves.
  • toolchain.json: every tool, its arguments, the targets, libraries and placeholders. Nothing about the toolchain is hard-coded in the GUI.
  • settings.json: one file at %APPDATA%\GRIDE. It is being reworked to one name per setting (§9).

6.1The C6747 chain: RTS6747, VM6747 and SIM6747

A build for target 2 runs: source → c90, cpp11 or shalimar with -arch tms6747 → C6000 assembly → asm6x (TI ELF objects) → lnk6x, with RTS6747 and a linker command file → .out. GRIDE can run the program at two points of that chain. VM6747 runs the assembly itself, before anything is assembled. SIM6747 runs the linked .out, the build's final output. Neither needs TI's tools or a board: the whole C6747 path, from compiling to debugging, is GRIDE's own.

RTS6747: the C and C++ run-time (rts6x.lib)

  • What it holds. The library every C6747 program links against: the C library (stdio, stdlib, string, ctype, math, time, locale); the C++ support (new and delete, exception handling with a variant without it, RTTI helpers); program start-up (the C auto-initialisation of .cinit, zero-filling and RLE24 decompression, then main and exit); and the EABI helper routines the compilers call for division, conversions and 64-bit arithmetic.
  • Host I/O. printf and file I/O reach the host through TI's CIO protocol, a buffer at C$$IO$$ that the simulator or a debugger services. The program's end is signalled at C$$EXIT. SIM6747 answers both.
  • Built by the toolchain itself. 353 C++ files (about 10,200 lines) in 16 areas and 24 assembly files, compiled for tms6747 by GRIDE's own cpp11, assembled by asm6x and packed by ar6x. All of it runs as build steps of the Visual Studio solution, with no batch file. There are two variants: rts6x.lib at -O2 for Release, and rts6xd.lib at -O0 with _DEBUG for Debug. The printf family is also packed on its own as printf6x.lib.
  • Beside it. The Shalimar run-time for the C6747 (shmrt6x.lib, linked before the C run-time it calls), and GRIDE's own linker command file for a project that brings none: one flat memory, every section placed, --rom_model, a 16 KB stack and a 1 MB heap.
  • Why it matters. TI's run-time (rts6740_elf.lib) is not needed. A project may still name TI's linker and run-time from a CCS or ti-cgt-c6000 installation.

VM6747: the emulator

  • What it does. Runs the compilers' C6000 assembly directly, a .s file or a folder of them, without asm6x or lnk6x. It models the C674x as far as the code needs: the two register files (A0–A15, B0–B15), the program counter, and the pipeline's visible property. A result lands some cycles after its instruction issues, and a branch takes effect five packets later, which is what the NOPs in the compilers' output are for. Parallel packets and the software-pipelined loop buffer are modelled too.
  • The C library, answered natively. A call to a C library or EABI helper lands on a stub, and the emulator answers it in C: it reads the arguments by the C6000 calling convention and returns in A4 (A5:A4). The heap sits above the program's data. So a program runs before any run-time library is linked. A Shalimar program takes its run-time as a folder of assembly.
  • Debugger. vm6747 --debug takes gdb's commands and answers in gdb's shapes: break, run, next, step, continue, finish, backtrace, info registers, args and locals, print, whatis, x, set. GRIDE drives it as it drives gdb. Since 2026-10-17 it also shows the variables of a -g build, from the .dwtag records the compilers write.
  • In GRIDE. Emulate, Run for a project marked "emulate only", and the debugger whenever the build has no .out with a line table.

SIM6747: the simulator

  • What it does. Loads the program image as TI's tools leave it: an ELF (EABI) or COFF .out, a hex6x image (TI-TXT, Intel or Motorola-S), or a raw binary. It runs the machine code cycle by cycle. Execute packets are fetched from memory and issued one a cycle, and each instruction reads and writes in the pipeline phases that TI's CPU reference (SPRUFE8, chapter 4) gives it: a result is seen only after its last delay slot, a branch lands after five, a load's word comes back in E5 and a store goes out in E3. Multi-cycle NOPs, the compact-header PROT bit, the control registers and the loop buffer (chapter 7) are modelled. At the end it prints CYCLES count=…, and the program's status is its exit code.
  • Host side. It services CIO through C$$IO$$ and stops at C$$EXIT, so a program linked against RTS6747 prints on the console as it would on a board under Code Composer Studio. It models no interrupts and no memory stalls.
  • Debugger. sim6747 --run --debug is GRIDE's debugging back end for target 2: the same gdb-shaped session as VM6747, but on the real linked program, stepping by the line table (TI's .dwpsn). Since 2026-10-17 it also shows variables, from the .gride.dwtag section that lnk6x carries into the image.
  • In GRIDE. Run for target 2, and the debugger when the .out is this build's and carries -g.

Why two runners

VM6747 answers before anything is linked, so the compilers' output is checked on its own and quickly. SIM6747 runs exactly what would be loaded onto the board, with RTS6747 and the memory layout lnk6x chose, and counts its cycles. GRIDE's Verify command runs both and compares the program's output line by line. That catches a fault in the assembler, the linker or the run-time that the emulator alone would not see.

7Optimisation: size and speed

This chapter says what each optimisation level does and what it was measured to be worth, on targets 1 and 2 in full and on targets 3 and 4 in brief. Every figure comes from cpp11's own records, with its date. Ratios are cpp11 ÷ reference: below 1 means cpp11 is faster or smaller.

All figures are from cpp11 1.5–1.8, dated 2026-09-21 to 2026-10-05. Versions 1.9 to 1.25 have correctness records only (§8.3); nothing yet measures 1.25.

7.1What the levels do

LevelWhat it does
-O0The default. No optimiser runs: the code is the walker's stack-machine output.
-O1The same pipeline as -O2, driven by size costs: fewer callee-saved registers for locals, rep movsq string copies, a tighter inliner, no division-by-constant rewrite, no invariant hoisting, no loop alignment.
-O2The same pipeline driven by speed costs: references weighted 8 per loop depth, unrolled block moves, the inliner's speed budgets, invariant hoisting, loop alignment. The model is Microsoft's: the level picks space or speed, not an amount of work.
-Os-O1 choosing the smaller code where the two differ. Implemented for target 2 only (division helpers kept when the function already calls something, the duplicated entry test off, a global's address held in a register); on the other targets -Os is -O1.
  • Target 1 (x86-64), after GCC's RTL scheme. Rounds of scalar passes (forward values, remove unreachable and dead code, coalesce copies, fold loads and offsets, thread jumps, divide by a constant), then the frame group (webs, locals into registers, register allocation, dead stores), then index folding, invariant hoisting, frame finishing, loop shrinking and alignment. A cost-driven inliner after GCC's ipa-inline decides calls in badness order under three budgets.
  • Target 2 (C6000), a pass over the emitted text. Locals in registers; list scheduling into execute packets with the branch delay slots filled; CALLP and BNOP; division by a constant; folded addressing; fills that store doublewords; frame-slot reuse; an inliner for callees of at most 12 AST nodes, nested up to three deep. At -O2 also software pipelining (modulo scheduling) and invariant hoisting.
  • Not built: vectorisation and unrolling on x86-64 (the matmul gap below), SPLOOP on the C6000, tail calls, if-conversion (cmov), global value numbering, an IR verifier.
  • What it declines. CPP11_DECLINES prints each transformation the optimiser holds back. The record of 2026-09-27 counts its declines per target and concludes that they do not explain the speed gap: none is in a hot loop.

7.5Compile speed

  • The Compiler++ harness for target 2 compiles in 16 s against cl6x's 533 s; at each level -O1 3.9 s, -O2 5.3 s, -Os 4.3 s (2026-10-07).
  • The sixteen Compiler++ sources at -O0, source to object (2026-09-05): Windows 0.29 s against cl's 0.94 s (8 jobs); Linux 1.20 s against g++'s 6.69 s (2 jobs); Mac 0.50 s against clang's 0.81 s (12 jobs).

7.6What the figures do not cover

  • cpp11 1.9 to 1.25. Their records are correctness gates, not timings.
  • A cpp11 -O0 against -O2 timing on target 1.
  • The earlier four-machine run that the 2026-09-27 table says it repeats; clang's version is known only from the 2026-09-05 benchmark page.
  • cppparse's own measurements (2026-10-20) measure the separate C++98 compiler, not cpp11; they are a contrast only. Against cl /O2 its code is 1.41× the size.

9Known limits and open work

  • Hosts. GRIDE runs on Windows x64 only. The tools have never been built on Linux or macOS from this tree.
  • cpp11. Brace member initialisers (: v{1, 2, 3}) are refused, by decision. A member template whose return type is the class's own typedef is refused. thread_local is refused. The exclusions document named in its source is not in the tree.
  • Windows tools. masm has no macros or conditional assembly. link writes no PDB, so Debug builds use clang and Microsoft's link.exe.
  • sim6747 models no interrupts and no memory stalls.
