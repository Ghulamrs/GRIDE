GRIDE Help

One toolchain in three outlooks - C90, C++11 and Shalimar for Windows and the TMS320C6747

1. The three outlooks

OutlookVersionWhat it is
BlackGRIDE 1.5.0Visual Studio's way: a workspace of several projects, Visual Studio's keys (White's on request)
GreyGRIDE 2.0.0Visual Studio's look with White's run and debug keys; one project at a time
WhiteGRIDE 1.0The simple one: RIDE's own window and its .pro projects

All three drive the same eleven programs, which sit beside GRIDE.exe: c90, cpp11, shalimar and c2s; masm, link and gride-dbg (GRIDE's debugger) for Windows; asm6x, lnk6x, sim6747 and vm6747 for the C6747, with RTS6x. All three read Code Composer Studio 7.4 / 5.5 projects without changing them. Black and Grey also read Visual Studio solutions. GRIDE's Setup installs one outlook at a time. Black and Grey also carry compile.dll, which plans their builds, and gride-plan.exe, which prints its plans from a command line (section 3).

2. First steps: the example

The example is cppparse, a C++ program in examples\projects\cppparse beside GRIDE.exe. GRIDE builds it with its own cpp11, masm and link, and links it with GRIDE's own C runtime for Windows (lib\x86_64-windows\grtc.lib and its layers, and GRIDE's kernel32.lib), so neither Visual Studio nor the Windows SDK is needed. Where Visual Studio is installed, Tools > Options > Projects > GRIDE Paths > Windows C runtime can choose Microsoft's CRT instead. Run it with --health ., and it reports on its own sources. Its cppparse.sln opens in Visual Studio as well.

The rest of examples\projects are projects in C, C++ and Shalimar, one with a third-party library, and the CCS samples; showcase holds three projects of several files - three equations solved in Shalimar and in C++, an average in C - that check their own answers, and shalimar-classic eleven single-file Shalimar programs, each with the lines it prints at its end. examples\programs holds single files, and examples\toolchain-demo\demo.ps1 runs all eleven programs from PowerShell. One examples folder serves the three outlooks. White copies both into Documents\GRIDE the first time it starts. All three outlooks read and write one .pro format, White's: a project saved in one opens in the other two.

Black switches to White's keys under Tools > Options > Environment > Keyboard, where F8, F7 and F6 debug and step, F4 builds, F5 runs and Ctrl+B builds the file in front. In all three a step over or into with nothing debugged (Black's F10 / F11, Grey's and White's F7 / F6) builds, starts the program and stops at main's first line, as Visual Studio does; debug, or carry on, runs to a breakpoint or the end. Every outlook lists its own keys: Help > Keyboard Shortcuts in Black and Grey, Help > Keys in White.

Dry run (Black since Setup 1.7.0, Grey since 1.8.0). Build > Dry Run - also in the menu that a right-click on a project in Black's Workspace Explorer, or on Grey's project tree, opens - writes the build of the project into the Output pane as a script and runs nothing. The first line is DRY RUN ONLY; then come the folder the commands run in, any file GRIDE would write for a tool (the C6747's ti-link.cmd, with its lines), and every command of a full build in order - each compile, each assembly and the link - written whole: the program by its path, every argument, quoted as Windows wants them, with the reason the tool was chosen on the line above it. It ends with what the commands would build and DRY RUN ONLY - end. Nothing is compiled, no folder is made, and the Error List and the last build's log stay as they were. In Black a project's dependencies come first, each with its own dry run, and Build > Dry Run Workspace - also in the workspace's right-click menu - takes every project of the workspace. A project read from Code Composer Studio's files or from a Visual Studio solution has its dry run too: the commands GRIDE would issue for it - cl's with the variables Visual Studio's tools are given, the C6747's with TI's options as GRIDE reads them - under a line planner that says the outlook's own planner wrote them. It is the script of a whole build, whatever is up to date. gride-plan.exe <project.pro> -dry, beside GRIDE.exe, prints the same from a command line.

Who plans a build (Black since Setup 1.7.0, Grey since 1.8.0). The commands of Build, Rebuild, Clean and Compile are planned by compile.dll, beside GRIDE.exe - one piece of code that the three outlooks are to share - and the outlook runs them and prints its log, the same text in Black and in Grey, which is also kept as obj\<Configuration>\<Target>\<project>.build.log (the one before as .build.previous.log); Build > Show Build Log opens it, with every command line whole, whatever the Output pane showed. A step that is up to date is not run, and the log says so in its place. Two things change with it for a project that stores no configuration of its own: the include folder inc and the define DEBUG or NDEBUG, which Black used to add to every compile whether or not the project asked, are no longer added - _DEBUG=1 and NDEBUG=1 come from the Compiler Options as before. A project that names them in Project > Properties keeps them. CCS and Visual Studio projects, Black's Assemble Only and Link Only, and a build while a tool under Tools > Options > Toolchains is changed from its defaults are still planned by the outlook itself, and the Output pane says so. In Grey the folders move with it (Setup 1.8.0): a project's program is written to out\<Configuration>\<Target> and its objects to obj\<Configuration>\<Target>, as in Black, where Grey wrote build\<Target>\<Configuration>; the old build folder of a project is left where it is and may be deleted. A configuration that names an output folder of its own keeps it, with its objects in obj under it. A file a project lists outside its build's groups is no longer compiled, and a changed Compiler Option rebuilds what it touches.

These are the versions of Setup 1.8.0. Every program answers --version in one shape: its name, its number and what it is in four words on the first line - masm 1.0 - x64 assembler, MASM syntax - and the copyright on the second; cpp11 adds the date it was sealed. Each runtime library holds a line of the same shape.

Help > About is the same box in the three outlooks, wider than it is tall and in the colours of the outlook that shows it - black in Black, grey in Grey, white in White - in four groups: the compilers first; the other tools next, the assemblers and linkers and, in Black and Grey, compile; then the runtime libraries with what debugs and simulates; and the three editors' versions at the end, the one that is running in bold. It asks every program and reads every library when it opens, so it shows what is installed, and a program that is missing or is not this release's shows as that. It does not wait for them: it opens at once with dimmed dots - c90 ... - for each line still being asked, and each line takes the place of its dots as soon as it answers, usually within a second or so. A compile.dll of another release shows as that too: compile - 9.9 found, this release's is 1.0 when the DLL beside GRIDE.exe is another release's. Black and Grey check compile.dll once more as they start, before their settings are read: if it is missing or another release's, the Output pane says so, and builds are planned by the outlook's own planner, with no dry run of a GRIDE project. compile.dll and gride-plan.exe also carry their number for Windows, in the file's Properties > Details. The About box's Copy button puts the whole of it on the clipboard, for a report.

How the numbers are given: a part built from another's sources is numbered with it - shmrt with shalimar, printf6x with RTS6x - and a part with sources of its own has its own number; masm, link and grt had none before Setup 1.6.3, and start at 1.0.

5. Where things are

  • Installed: %LOCALAPPDATA%\Programs\GRIDE\<outlook> for one user, or C:\Program Files\GRIDE\<outlook> for everyone. The folder holds GRIDE.exe, the programs (with compile.dll and gride-plan.exe in Black and Grey), include\ (the headers: c, c++ and win), lib\ (the runtimes: x86_64-windows and tms6747), share\ccs (TI's option tables), src\runtime (the runtimes' sources, for the debugger), docs\ (these pages) and examples\. Settings > Apps > GRIDE removes it - and with it everything GRIDE wrote, so that the next installation starts clean: the outlook's folder whole, with whatever was built or saved inside it; your settings, %APPDATA%\GRIDE; White's own state, %USERPROFILE%\.gride\state.json; and GRIDE's files in %TEMP%. A newer Setup installed over an older one removes the older the same way, so the settings start afresh then too. Projects kept anywhere else - Documents\GRIDE among them - are never touched: copy what you want to keep out of the installed examples\ first.
  • Your settings: one file, %APPDATA%\GRIDE\settings.json, whichever outlook is installed; each keeps its own keys in it and leaves the others'. A file from before - Black's gride.settings.json beside it, White's %USERPROFILE%\GRIDE 1.0\settings.json - is taken in the first time and then removed. White's settings.json beside GRIDE.exe holds the installation's defaults, under yours. In a portable copy, Black and Grey keep the file beside GRIDE.exe when it is there.
  • The toolchain: Black and Grey read one toolchain.json beside GRIDE.exe, with your changes in %APPDATA%\GRIDE\toolchain.json. The file holds settings only; Settings Files says what each entry is, and its format what each field may hold. White finds each program beside itself.
  • From source: each outlook's GRIDE.sln (Visual Studio 2022's format, v143) builds GRIDE.exe and the eleven programs into x64\<Config> - Black's and Grey's also compile.dll and gride-plan.exe (common\compile) - and GRIDE3.sln beside them builds the three outlooks and the Setup. If Visual Studio 2026 offers to retarget to v145, answer Ignore all.

6. References

The Help menu's Language Reference opens C90, C++11 and Shalimar. Toolchain Reference opens MASM / LINK, ASM6x / LNK6x, RTS6747 and VM6747 / SIM6747. These pages point into RIDE 5.17's complete manual, which describes the compilers, the languages and the targets in full. Settings Files explains toolchain.json, settings.json and the .pro project file. GRIDE Design and Development (2.0) is the project's report: GRIDE and its toolchain - the platforms, the languages, the GUI, the compilers, their optimisation, how they were developed and checked, and what is still open.
