1Introduction

1.1Purpose

This report records how GRIDE is designed, how it is built, and how far it has been verified. It is written for the engineers who maintain or extend GRIDE and for reviewers who need its scope, its standards, its measured quality and its limits in one place.

1.2Scope

  • The GUI: GRIDE, version 1.5.0.0: editor, projects and workspaces, build, run and debug.
  • The whole toolchain GRIDE drives: c90, cpp11, shalimar, asm6x, lnk6x, RTS6747 with ar6x, SIM6747, VM6747, masm, link with its librarian, gride-dbg and grt.
  • Four targets: 1. x86_64-windows and 2. tms6747 (the TI TMS320C6747 DSP), the two complete ones; 3. x86_64-linux and 4. arm64-darwin, reached as far as assembly.
  • The Setup that installs GRIDE and its toolchain, and the project that builds it.

1.3Baseline

Facts are taken from the GRIDE repository at commit ede17c0 (2026-10-27), 60 commits after 1.0's baseline 6090472. It holds cpp11 1.30 and the cppparse example at its repository's bf0c3f7, whose sources are those of that repository's latest commit, 2dec723. The records and reviews used are listed in chapter 10. No work above the baseline is described. Where the old RIDE 5.17 manual and the source disagree, the source is followed.

1.4Conventions

  • Target numbers. The four targets keep the numbers 1 to 4 of §1.2 throughout.
  • Ratios are GRIDE's figure divided by the reference's: below 1 means GRIDE's tool is faster or smaller.
  • Refused by name means the compiler stops with a message that names the unsupported feature, rather than compiling it wrongly. It is the toolchain's rule for anything it does not implement.
  • An oracle is a reference compiler, simulator or run-time whose result decides what is right (§8.2).
  • A † in chapter 10 marks a standard the sources name by subject but not by number.

2System overview

GRIDE is a Windows IDE built around its own compiler toolchain. The GUI holds the editor, projects and workspaces, the build, the run and the debugger. Every tool it starts, and every switch it passes, is defined in toolchain.json, so the GUI itself names no tool. Projects are .pro files, the settings live in one settings.json, and the Help is a set of HTML pages beside the program.

2.2Design principles

  • The toolchain is data. A renamed program or a changed switch is a change to toolchain.json, not to the GUI.
  • Own tools end to end on the two complete targets. From source to a running, debuggable program, neither target needs a vendor tool, though either may use one. Since this version's baseline that holds for target 1's Debug builds, its run-time and its debugger as well.
  • Refuse by name. A feature a tool does not implement stops it with a message naming the feature.
  • Measured against oracles. Every tool was written against a reference: cl, g++, clang, TI's cl6x, ml64 and link.exe, and Microsoft's run-time for grt (§8.2).
  • Inspiration, not copies. Microsoft's run-time sources are read for behaviour, layouts and edge cases; none of their text is in GRIDE.
  • No shell. Every tool starts the next one directly, so builds, and the Setup's build, work where cmd.exe is disabled by policy.

3.3The pipelines

  • Target 1, Release: the compiler writes MASM-spelled assembly (-S -masm=masm); masm makes an MS COFF object; link makes a PE32+ console program against the C run-time GRIDE chose for the build.
  • Target 1, Debug: the same road with -g. The compiler writes the .FILE and .LINE directives and its CodeView records in the MASM spelling (-g -masm=masm); masm carries them in .debug$S and .debug$T; link /DEBUG writes the PDB that gride-dbg, cdb and Visual Studio read. No clang and no Microsoft link.exe are needed. That older road, the GNU spelling assembled by clang and linked by link.exe, is kept for a compiler that names no CodeView spelling of its own in toolchain.json; since cpp11 1.29 none of GRIDE's three needs it.
  • Target 1, the C run-time: grt, GRIDE's own: its five libraries and its kernel32.lib named by their paths, Microsoft's libraries refused with /NODEFAULTLIB; or Microsoft's static CRT (libcmt, libucrt, libvcruntime, kernel32, legacy_stdio_definitions) found through LIB. The setting's default, auto, takes Microsoft's only where Visual Studio is found and the build has cl's objects, grt otherwise; GRIDE_WINDOWS_RUNTIME=grt or msvc in the environment at start wins. The Shalimar run-time follows the choice, and the Output says it once a build.
  • Target 2: the compiler writes TI C6000 assembly; asm6x makes TI ELF objects; lnk6x links them with RTS6747 under a linker command file (GRIDE's own when the project has none); SIM6747 runs the image. Emulate runs the assembly on VM6747 instead, and Verify runs both and compares their output line by line.
  • Targets 3 and 4: assembly only on Windows; on their own machines the host's assembler and C or C++ driver finish the build.
  • A lone file with a main, opened with no project, builds as its own program beside the file.

4.2What GRIDE compiles

C: c90 1.3

c90 implements ISO/IEC 9899:1990 (C90, ANSI X3.159-1989) for all four targets and ships its own 16 C90 headers. It refuses C++ source by suffix. It optimises (-O1, -O2) in its x86-64 back end only. Since 1.0 it probes a frame of a page or more with __chkstk on target 1, as cl does; calls setjmp with nothing parked on the stack, so (n = setjmp(jb)) == 0 no longer loops at -O0; takes function declarators in a file-scope declaration list; and writes its own CodeView under -g -masm=masm (§6.4).

C++: cpp11 1.30

cpp11's claim is its banner: C++03 with C++11 extensions. It compiles ISO/IEC 14882:2003 and a large part of ISO/IEC 14882:2011, ships 39 C++ and 23 C headers of its own, and refuses by name what it does not implement. Its source cites the standard by its stable clause names, 423 of them.

An independent review measured this breadth on 268 valid programs judged by cl and by clang++ in strict C++11 (§8.4). cpp11 1.25 ran 99 of them as cl does and refused 134. cpp11 1.27 runs 164 as cl does, differs on 11 and refuses 85, with no program that worked before going wrong.

Since 1.27: 1.28 fixed the review's wrong-code set and three of its four accepted ill-formed programs (§9.1); 1.29 writes its own CodeView for GRIDE's masm, every name whole with its namespaces as cl's PDB spells it (§6.4); 1.30 made three fixes grt needed: p - n with n narrower than the pointer is widened before it is negated, a C name that is a MASM keyword (fabs, C90's div) stays the symbol's name, and a dynamic initialiser under -g names the labels its code defines. Its <algorithm> gained both forms of std::equal, and an enum inside a class is mangled through the class. The review's programs were run again as a gate of 1.30's fixes and recorded unchanged; the counts above are still 1.27's, as no later run counted them again.

Shalimar: shalimar 1.3, the micro compiler

Shalimar is a micro language: a small compiled language of its own, defined by its author's Shalimar 1.3 specification. Every Shalimar file has a main, and the Shalimar run-time owns the program's entry point, so a program is one compilation of the file with main and the files it calls into. shalimar compiles for all four targets and links with its run-time on targets 1 and 2. Since 1.0 its errors take the form c90 and cpp11 use, file:line:col: error: with the source line and a caret, and it writes its own CodeView under -g -masm=masm.

5The GUI: GRIDE

GRIDE is a C++/CLI WinForms application of 60 source files. Its class map and main flows are documented in the source tree's ARCHITECTURE.md. The Setup installs it in one of three outlooks: Black, the default; Grey; and White, The Simple. Each outlook is a solution of its own over the one toolchain, and on 2026-10-26 Grey and White were brought to Black's features. This report describes GRIDE in the Black outlook.

5.1What it offers

  • Editing: a code editor with syntax colouring for C, C++, Shalimar and assembly; docking panes; three themes; Visual Studio's keys, or the simple key set on request; snippets; external tools; a terminal pane.
  • Projects: .pro projects and .grws workspaces of several projects with a startup project, dependencies and build order. Code Composer Studio 7.4 and 5.5 projects, and Visual Studio solutions and projects, are read as they are, read-only.
  • Build: build and rebuild a workspace, a project or a file; clean; assemble only; link only; batch build; a configuration manager. A project's files are compiled side by side, one per processor, and the Output pane and the Error List keep the project's order (§5.3).
  • Run: an output pane with an input line; Emulate on VM6747; Verify on SIM6747 and VM6747 together.
  • Debug: breakpoints, stepping, the call stack, locals, watch and memory, through gride-dbg, cdb, SIM6747, VM6747, gdb, lldb or the Shalimar run-time's own session. F10 or F11 with nothing being debugged builds the program, starts it and stops at main's first statement; the debugged program reads the line typed under the Output pane (§5.5).
  • Choices for target 1, under Tools > Options: the Windows debugger (auto, gride-dbg or cdb) and the C run-time a program links (auto, grt or Microsoft's).
  • Help: F1 opens the Help the three outlooks share; Help › About names cpp11's version as cpp11 itself gives it (§5.8).

5.3How a build runs

  1. The main form starts the build engine on a worker thread.
  2. For each project, in build order: Clean and Rebuild are honoured, a project folder that cannot be written is refused, and the macros of the project and configuration are set.
  3. For each source, the compiler is chosen: the group's word, else the project's, else the language's. A Shalimar program is compiled as one unit.
  4. The tool's command line comes from toolchain.json (§5.4), each $(…) placeholder filled by the macro expander; an unknown placeholder is left visible rather than dropped.
  5. Every compile and assembly of the project is decided first, in project order, with its checks: a refusal, a tool not found, a step already up to date. The steps then run side by side, the largest source first, each on a runner of its own. Each finished step is read back in project order, so the Output pane, the Error List and the first error are what one tool after another would have given. The first step to fail stops the others, and a failed step's output file is removed, so half an object never looks up to date. Files compiled at once under Tools > Options (buildJobs: 0, the default, one per processor; 1, one at a time) sets how many run.
  6. The objects are linked: masm and link on target 1, against the C run-time chosen for the build (§3.3); asm6x and lnk6x with RTS6747 on target 2. If the toolchain's own assembler or linker fails, GRIDE offers the vendor's tools for that build.
  7. Each tool is started directly, in a job object, with no shell. cmd.exe is used only when the user configures a setup script.
  8. Output, messages and the finish event return to the Output pane and the Error List. The Output pane shows a project's file by its path from the project's folder, and the Error List keeps the full path for navigation. A tool's output is capped at 40 lines in the pane, and GRIDE never opens a generated .s as if it were the source of an error.

On cppparse's Release rebuild on 12 processors, the side-by-side build took 49.6 s against 190.3 s one tool at a time, with the same 134 lines of output (2026-10-26).

5.4How toolchain.json drives the tools

The file has these sections: installation (where the toolchain lives), ccs (reading CCS projects), compilerOptions (17 options on four tabs), visualStudio (finding cl, link.exe, clang and the Windows SDK without vcvars), placeholders (44), targets (4), tools (23), libraries (7) and linkerCommandFiles. A target names a tool for each role (C, C++ and Shalimar compilers, assembler, linker, debug assembler, debug linker, the vendor's assembler and linker, simulator, emulator, GRIDE's own debugger, the debugger and its fall-back) and its C run-time. A tool names its operations, each a command line such as cpp11's:

-S "$(Source)" -o "$(AsmFile)" $(ArchFlag) $(ConfigFlags) $(AsmSyntaxFlag) $(IncludeFlags) $(DefineFlags) $(CompileFlags)

Since 1.0 the file names gride-dbg, in the role ownDebugger with a session in cdb's dialect, and two libraries: grt and the Shalimar run-time built over it. A library for target 1 says which C run-time it belongs to (crt: grt or msvc), so GRIDE links the Shalimar run-time that matches the program's. A tool is found by its environment variable, then beside GRIDE.exe and in the installation's bin, then in Visual Studio's or TI's folders when its lookup says so, then on PATH. The user's own %APPDATA%\GRIDE\toolchain.json overrides the shipped file field by field. The shipped file is crisp: settings only, 59 KB, with one-line labels where the Options pages show them; what every entry means is in the Help (Settings_Files.html).

5.5How debugging runs

F5 builds, then the debugger choice picks an engine from the target's roles and the tool's session. For target 1 it is gride-dbg (§6.5) when it is beside GRIDE, else cdb, else lldb; the setting can name gride-dbg or cdb, the other standing in where the one named is missing, and the Output says which and why. For target 2 it is SIM6747 or VM6747; on their own machines gdb or lldb; for a Debug Shalimar program the Shalimar run-time's own session. The process debugger sends one command at a time, ended by a marker, over pipes or a pseudo-console; the transcript reader turns the gdb-, lldb- or cdb-shaped answers into stops, frames and variables, and a stop refreshes the panes. gride-dbg answers in cdb's shapes, so the same reader serves both. When nothing can debug a build, GRIDE says why.

  • Starting at main. F10 or F11 with nothing being debugged builds, starts and stops at main's first statement, as Visual Studio does: a one-shot breakpoint on main's line (C's and C++'s int main(, Shalimar's fun <> = main), then one step past its prologue. F5 still runs to a breakpoint or the end.
  • The program's input and output. The line typed under the Output pane goes to the debugged program at once, even while it runs (gride-dbg's .input). The program's output is shown while it runs and at every stop. A line it has not finished is shown as far as it goes and joined to its rest when that comes, never repeated.
  • Values as the language shows them. A Shalimar array by its elements, cpp11's vector, string and initializer_list by what they hold, a reference as what it refers to. A watch of a name the stop cannot see says "not in scope here".

5.8Where GRIDE states versions

A version number written into GRIDE would be a second copy of the tool's own, and the one that goes stale. So GRIDE states cpp11's version by asking cpp11, and the few texts that name it say 1.30.

  • Help › About, in each outlook, runs the cpp11 the toolchain resolves with --version when the box opens. It shows cpp11's banner without the copyright, then the version line cpp11 writes beneath it: "C++03 with C++11 extensions, Version 1.30, sealed 23-10-2026". When cpp11 is not found or does not answer, the box says so. White shows it among its rows for shalimar, c90 and c2s, which give their own banners; shalimar's and c2s's carry their numbers, c90's names none.
  • Written texts that name the version in use say 1.30: the Help's version table, the installer test's default, and GRIDEd's Help › Release Notes, which also lists gride-dbg and grt. Runtime_Design.md said 1.29 there, and the macOS tree's help page RIDE's 1.5 and 1.8; both were corrected on 2026-10-27. Versions named as history, such as when a feature came in or the 1.29 bugs that 1.30 fixed, stay as they are.
  • Where the number comes from. cpp11's own Version.h: CXX1_VERSION "1.30", the seal file cxx1-1.30.dat and the seal date 23-10-2026, with a history line for each version (§4.2).

6.1The compilers' design

Each compiler is one program, and each runs its phases in one process, without a shell. cpp11, the largest, is described here as an independent review read it (§8.4); c90 and shalimar follow the same shape on a smaller scale.

  • Preprocessor. Works on text lines: macros are body strings and #if is evaluated on 64-bit integers. Its output is one preprocessed text and a map back to the source lines. Since 1.27 it handles a UTF-8 byte-order mark, unsigned arithmetic in #if, _Pragma, and the rescan of a macro name left at the end of an expansion.
  • Lexer. Turns the whole text into one vector of tokens.
  • Parser, with semantic analysis and lowering in the same pass. A recursive-descent parser of about 26,000 lines. As it reads, it resolves names and overloads, lays out classes, builds vtables, RTTI records and the target's exception tables, and lowers the program to a C-level tree: variables with frame offsets, member accesses with byte offsets, calls with decorated names, references as pointers.
  • Templates by token replay. A template is kept as its range of tokens. An instantiation re-reads that range with the parameters bound, until no instantiation is pending. Partial specialisations are matched as patterns, and SFINAE is a trial parse whose failure is a substitution failure.
  • Back ends. One walker per target emits instructions through a spelling interface: MASM or GNU for x86-64, Apple arm64, TI C6000. The optimiser sits in front of the spelling as a decorator (chapter 7). Under -g the MASM spelling also carries the lines and the CodeView records, as data directives that GRIDE's masm assembles (§6.4). Both C++ name manglers, Microsoft's and Itanium's, live in one module.
  • Diagnostics. The first error stops the compilation with file:line:col, a sentence that names the rule or the limit, and the candidates where overloads are concerned. Since 1.26 the compiler runs on a 256 MB stack and bounds its nesting by name, where 80 parentheses or a 40-deep template recursion used to crash it.

6.2The C6747 chain: RTS6747, VM6747 and SIM6747

A build for target 2 runs: source → c90, cpp11 or shalimar with -arch tms6747 → C6000 assembly → asm6x (TI ELF objects) → lnk6x, with RTS6747 and a linker command file → .out. GRIDE can run the program at two points of that chain. VM6747 runs the assembly itself, before anything is assembled. SIM6747 runs the linked .out, the build's final output. Neither needs TI's tools or a board: the whole C6747 path, from compiling to debugging, is GRIDE's own.

RTS6747: the C and C++ run-time (rts6x.lib)

  • What it holds. The library every C6747 program links against: the C library (stdio, stdlib, string, ctype, math, time, locale); the C++ support (new and delete, exception handling with a variant without it, RTTI helpers); program start-up (the C auto-initialisation of .cinit, zero-filling and RLE24 decompression, then main and exit); and the EABI helper routines the compilers call for division, conversions and 64-bit arithmetic.
  • Host I/O. printf and file I/O reach the host through TI's CIO protocol, a buffer at C$$IO$$ that the simulator or a debugger services. The program's end is signalled at C$$EXIT. SIM6747 answers both.
  • Built by the toolchain itself. 364 C++ files and 24 assembly files, 12,973 lines in all,, compiled for tms6747 by GRIDE's own cpp11, assembled by asm6x and packed by ar6x. All of it runs as build steps of the Visual Studio solution, with no batch file. There are two variants: rts6x.lib at -O2 for Release, and rts6xd.lib at -O0 with _DEBUG for Debug. The printf family is also packed on its own as printf6x.lib.
  • Beside it. The Shalimar run-time for the C6747 (shmrt6x.lib, linked before the C run-time it calls), and GRIDE's own linker command file for a project that brings none: one flat memory, every section placed, --rom_model, a 16 KB stack and a 1 MB heap.
  • Why it matters. TI's run-time (rts6740_elf.lib) is not needed. A project may still name TI's linker and run-time from a CCS or ti-cgt-c6000 installation.
  • Since 1.0. C99's log2, hypot, cbrt, strtoll, strtoull, strtof, strtold and vsnprintf, for both targets; log no longer depends on the order of evaluation, and pow(-1, y) is ±1 however large y is. Its C library is also the base of grt's, compiled for Windows (§6.6); the C6747's code is unchanged by that.

VM6747: the emulator

  • What it does. Runs the compilers' C6000 assembly directly, a .s file or a folder of them, without asm6x or lnk6x. It models the C674x as far as the code needs: the two register files (A0–A15, B0–B15), the program counter, and the pipeline's visible property. A result lands some cycles after its instruction issues, and a branch takes effect five packets later, which is what the NOPs in the compilers' output are for. Parallel packets and the software-pipelined loop buffer are modelled too.
  • The C library, answered natively. A call to a C library or EABI helper lands on a stub, and the emulator answers it in C: it reads the arguments by the C6000 calling convention and returns in A4 (A5:A4). The heap sits above the program's data. So a program runs before any run-time library is linked. A Shalimar program takes its run-time as a folder of assembly.
  • Debugger. vm6747 --debug takes gdb's commands and answers in gdb's shapes: break, run, next, step, continue, finish, backtrace, info registers, args and locals, print, whatis, x, set. GRIDE drives it as it drives gdb. Since 2026-10-17 it also shows the variables of a -g build, from the .dwtag records the compilers write.
  • In GRIDE. Emulate, Run for a project marked "emulate only", and the debugger whenever the build has no .out with a line table.

SIM6747: the simulator

  • What it does. Loads the program image as TI's tools leave it: an ELF (EABI) or COFF .out, a hex6x image (TI-TXT, Intel or Motorola-S), or a raw binary. It runs the machine code cycle by cycle. Execute packets are fetched from memory and issued one a cycle, and each instruction reads and writes in the pipeline phases that TI's CPU reference (SPRUFE8, chapter 4) gives it: a result is seen only after its last delay slot, a branch lands after five, a load's word comes back in E5 and a store goes out in E3. Multi-cycle NOPs, the compact-header PROT bit, the control registers and the loop buffer (chapter 7) are modelled. At the end it prints CYCLES count=…, and the program's status is its exit code.
  • Host side. It services CIO through C$$IO$$ and stops at C$$EXIT, so a program linked against RTS6747 prints on the console as it would on a board under Code Composer Studio. It models no interrupts and no memory stalls.
  • Debugger. sim6747 --run --debug is GRIDE's debugging back end for target 2: the same gdb-shaped session as VM6747, but on the real linked program, stepping by the line table (TI's .dwpsn). Since 2026-10-17 it also shows variables, from the .gride.dwtag section that lnk6x carries into the image.
  • In GRIDE. Run for target 2, and the debugger when the .out is this build's and carries -g.

Why two runners

VM6747 answers before anything is linked, so the compilers' output is checked on its own and quickly. 6.3The Windows tools: masm and link

Both came from RIDE 5.17 and have grown in GRIDE since 1.0, masm by 706 lines and link by 1,777, for the debug information of §6.4 and for grt (§6.6). Both are built on the static VC++ run-time, as the other toolchain programs are.

  • masm assembles the MASM spelling the compilers write into MS COFF AMD64 objects, with COMDAT and associative sections and the .pdata/.xdata unwind tables of PROC FRAME. It was held to ml64 byte for byte on the compilers' output. It takes the directives that output uses (sections, PROC/ENDP with the unwind directives, data definitions, EQU, PUBLIC/EXTERN, OPTION, and OPTION NOKEYWORD as ml64 takes it); it has no macros and no conditional assembly. New since 1.0:
    • CodeView. A .debug$S section per object: the object name and compiler records, a procedure record and S_FRAMEPROC for each PROC, and a line table from the .FILE and .LINE directives (or the assembly's own lines under /Zi, as ml64); an associative .debug$S for each COMDAT procedure; the compilers' type records carried in .debug$T. A repeated .LINE makes a line entry of its own, so a one-line function's body has a line after its prologue.
    • The instructions grt needs, for its start-up, its mem* routines and setjmp, each checked byte for byte against ml64.
    • Lookup by name through an index, not a walk of every symbol.
  • link links MS COFF objects and libraries, short import members included, into a PE32+ console program with the Rich header, base relocations, the load-configuration and TLS directories, and a debug directory. It resolves Microsoft's C run-time through libcmt's default libraries, takes the usual switches (/out, /entry, /subsystem, /stack, /libpath, /nodefaultlib, /opt:ref,icf, /map …) and was held to link.exe byte for byte on its test bed. Without /DEBUG its images are as they were. New since 1.0:
    • The PDB. /DEBUG (and /PDB:file) writes an MSF PDB and names it in the image's debug directory (§6.4).
    • The librarian. link /LIB (or -lib) writes COFF archives: the first and second linker members, the longnames member, deterministic headers, and a warning for a name two members define unless both are COMDAT. From a .def file (/DEF) it writes an import library in the Windows SDK's layout: the import descriptor, the null descriptor and the null thunk, then one short import member per export, with the hint its sorted place gives it. /LIST prints an archive's names, and @response files work in both modes (src\librarian.cpp).
    • Why it matters. grt's five libraries and its kernel32.lib are written this way, so neither lib.exe nor the Windows SDK's libraries are needed to build a program for target 1.

6.6grt: the run-time for target 1

grt (toolchain\Windows\RT) is GRIDE's own C and C++ run-time for Windows. A program linked against it imports kernel32.dll alone and runs on any machine with Windows and GRIDE's installation, without Visual Studio and without the Windows SDK. Its design is docs\Runtime_Design.md, draft 3, accepted on 2026-10-23.

  • Built by GRIDE's toolchain only. c90 compiles its C, cpp11 its C++, masm its assembly, and link /LIB packs its libraries and writes kernel32.lib from kernel32.def. cl, ml64, lib.exe and Microsoft's link.exe never build it.
  • Correctness is the gate, efficiency the aim. A program on grt prints what the same objects print when linked with Microsoft's static CRT: stdout and stderr byte for byte, and the same exit code. It is to be at least as fast as that CRT on the benchmark set, every test within 5 % or faster from stage 2's exit, and its programs smaller.
  • Microsoft's sources are inspiration only. vcruntime and the UCRT are read for sequences, data layouts and edge cases, such as the tables cpp11 emits, the initialiser order and what printf prints for a NaN. None of their text is in GRIDE. RTS6747's C library is the base of grt's: the same sources, compiled for Windows, under a stream layer of Windows' own.
  • Limits. Target 1 only; console programs (main) first; the "C" locale, with narrow characters in the ANSI code page.

What is inside

  • Streams. A FILE has a 4 KB buffer. Files, pipes and NUL are fully buffered; a console and stderr are written as each call ends, as Microsoft's are, so output is identical and a debugger sees an unfinished line. Reads keep raw bytes and translate CR LF and CTRL+Z as they hand them out, so a position never costs a seek per fill. A large binary fread or fwrite bypasses the buffer, as the UCRT's does, and the character functions have buffer fast paths. Up to 512 FILEs and 8,192 descriptors, as Microsoft's.
  • Memory. memcpy, memmove and memset in tiers: SSE2, AVX where Windows has it, rep movsb/stosb from 2 KB where the processor reports ERMSB; the 4 KB aliasing case is copied backwards.
  • Microsoft's behaviour where a program can see it. abort, a failed assert, _purecall and a null FILE * end by the fast fail (0xC0000409), as Microsoft's Release run-time does. A domain error answers -nan(ind); strtod gives ERANGE only for a zero or infinite result. system runs %COMSPEC% /c as the UCRT's does; where cmd.exe is refused by policy it prints the refusal and answers 255.

LevelWhat it does
-O0The default. No optimiser runs: the code is the walker's stack-machine output.
-O1The same pipeline as -O2, driven by size costs: fewer callee-saved registers for locals, rep movsq string copies, a tighter inliner, no division-by-constant rewrite, no invariant hoisting, no loop alignment.
-O2The same pipeline driven by speed costs: references weighted 8 per loop depth, unrolled block moves, the inliner's speed budgets, invariant hoisting, loop alignment. The model is Microsoft's: the level picks space or speed, not an amount of work.
-Os-O1 choosing the smaller code where the two differ. Implemented for target 2 only (division helpers kept when the function already calls something, the duplicated entry test off, a global's address held in a register); on the other targets -Os is -O1.
  • Target 1 (x86-64), after GCC's RTL scheme. Rounds of scalar passes (forward values, remove unreachable and dead code, coalesce copies, fold loads and offsets, thread jumps, divide by a constant), then the frame group (webs, locals into registers, register allocation, dead stores), then index folding, invariant hoisting, frame finishing, loop shrinking and alignment. A cost-driven inliner after GCC's ipa-inline decides calls in badness order under three budgets.
  • Target 2 (C6000), a pass over the emitted text. Locals in registers; list scheduling into execute packets with the branch delay slots filled; CALLP and BNOP; division by a constant; folded addressing; fills that store doublewords; frame-slot reuse; an inliner for callees of at most 12 AST nodes, nested up to three deep. At -O2 also software pipelining (modulo scheduling) and invariant hoisting.
  • Not built: vectorisation and unrolling on x86-64 (the matmul gap below), SPLOOP on the C6000, tail calls, if-conversion (cmov), global value numbering, an IR verifier.
  • What it declines. CPP11_DECLINES prints each transformation the optimiser holds back. The record of 2026-09-27 counts its declines per target and concludes that they do not explain the speed gap: none is in a hot loop.

8Development and verification

8.1Repository and build

  • Repository. GRIDE lives in a local bare repository (GIT Test\GRIDE); the working copy is GRIDE3. Each tool tree inside it is a minimal copy of the tool's own repository: source, project files and headers, without tests, build output or release seals. gride-dbg and grt live only here, with grt's tests and benchmarks beside its sources.
  • Build. Three Visual Studio solutions, one per outlook (GRIDEd\GRIDE.sln, GRIDE 2.0\GRIDE.sln and GRIDE 1.0\GRIDE.sln), each build GRIDE and the whole toolchain into x64\Debug and x64\Release: every tool program, gride-dbg, RTS6747 in both variants, grt's five libraries and kernel32.lib, and the Shalimar run-time for both complete targets, on Windows over Microsoft's CRT and over grt. The run-time builds are MSBuild steps, so no step goes through cmd.exe and a build inside Visual Studio does what a command-line build does. The solutions are built one at a time, since their tool projects share their build folders.
  • Verified in Visual Studio before every commit, with Visual Studio's own build (devenv) in Release and Debug. A Rebuild of one solution after another deletes the earlier one's programs, so a Rebuild is followed by plain Builds; projects with custom build steps turn off Visual Studio's fast up-to-date check, so those steps always run.
  • The Setup project. installer\windows\Setup.vcxproj is a C++ Utility project in each solution, listed after GRIDE and not built with it, and the one project of installer\windows\Setup.sln. Its Release build runs build-setup.ps1, which writes the MSI through Windows Installer's own automation interface (msi.dll) and makecab, then validate-msi.ps1, which runs the Windows SDK's ICE suite where the SDK is installed. An inline MSBuild task starts each program directly, never through cmd.exe, and shows its lines as they come; Debug refuses, naming Release. Setup.sln builds the three solutions one after another, each in an MSBuild of its own, then the package. Nothing beyond Visual Studio's C++ workload is needed: no WiX, no Inno Setup, no NuGet package and no Installer Projects extension.
  • Setup 1.5.0. One MSI that installs one outlook per user, without elevation: Black by default, Grey or White when chosen on its second screen. Each outlook comes with the toolchain beside it, grt's libraries and gride-dbg, the Help and the docs, the examples, and Visual Studio's VC++ run-time DLLs beside GRIDE.exe, the one program that needs them. It is validated by the ICE suite and by an install test that installs each outlook in turn, checks it, repairs it and removes it. Signing is ready in the script and waits for a certificate (§9.2).

9.3The other tools

  • masm has no macros and no conditional assembly; the compilers do not need them.
  • link's PDB has the open points of §6.4: source checksums, inlined calls' lines, type servers.
  • gride-dbg debugs console programs of target 1; cdb and lldb remain its stand-ins.
  • SIM6747 models no interrupts and no memory stalls.
  • VM6747 is not an oracle: it once agreed with two wrong outputs that only TI's simulator exposed.
  • c90 does not optimise on target 2.

9.4grt

  • Exceptions are stage 2's next step: on grt, _CxxThrowException ends the program saying what was thrown. A C++ program that throws needs Microsoft's run-time until then.
  • Threads. The tables are locked (§6.6), but errno, strtok's state and localtime's result are still shared, not one per thread, and a thread started without grt's CreateThread is not seen.
  • Speed. str* 4 to 44 times Microsoft's, sin, exp, log and pow 2 to 3.7 times, printf to a file 1.3 to 1.7 times: stage 2's SSE2 str*, kernels and fast paths.
  • The catalogue. _access, _chdir, _mkdir and _rmdir are left, 153 of 157 done.
  • Found, to settle in stage 2. The UCRT returns an sNaN quieted, sets no ERANGE on exp's and pow's underflow and has its own NaN rules for pow; its printf fails fast on %n and pads %s with zeros under the 0 flag.
  • Later. The layout of stage 3, Shalimar's direct access of stage 4, then wmain, WinMain, UTF-8, wide characters and a DLL.
